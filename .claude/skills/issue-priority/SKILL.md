# Issue 優先度スキル（/issue-priority）

入力: **$ARGUMENTS**

Open Issue の消化優先度を判定し、順位表と `priority:*` ラベル案を出す。ラベルはユーザーの承認を得てから付け替える。**このスキルでは実装・起票・Issue 本文の編集を行わない**。

## 使い方

```
/issue-priority
/issue-priority #475 #476
```

- 入力が無ければ、Open Issue 全件（`meta` / `question` ラベルの Issue と #2 のテンプレート Issue を除く）を対象にする
- Issue 番号を指定したら、順位表とラベル案はその Issue だけに絞る。依存関係（後続を塞いでいるか・依存先が閉じているか）の判定には全件を使う

## 手順

### 1. 集める

1. GitHub MCP の `list_issues`（`state: OPEN`、`fields: ["number", "title", "labels"]`）で Open Issue を一覧する
2. `list_pull_requests`（`state: open`、`fields: ["number", "title", "body", "draft", "head", "mergeable_state"]`）で Open PR を一覧し、タイトル末尾の `#N` と本文の `closes #N` で Issue に紐づける
3. `git ls-remote --heads origin` でリモートのブランチを取り、`*/#<番号>-*` に当たるものを Issue に紐づける

GitHub MCP が使えなければ `gh issue list` / `gh pr list`（`.claude/rules/mcp-setup.md`「利用不可時のフォールバック」）で同じ情報を取る。

### 2. 要約する

対象が **4 件以上** なら、本文とコメントの読み込みを `general-purpose` エージェントに任せ、要約だけ受け取る（`code-explorer` は GitHub MCP を持たない）。3 件以下なら自分で `issue_read`（method: `get` / `get_comments`）を読む。委譲プロンプトの例：

```
目的: Open Issue の消化優先度の判定材料を集める。読み取りのみ（コメント・ラベル・本文の書き込みはしない）。
対象: #A, #B, ...（ToolSearch で select:mcp__github__issue_read をロードし、method=get。コメントがあれば get_comments、親子関係があれば get_parent / get_sub_issues）
各 Issue について 6 行以内で返す:
- 目的（1 行）
- 依存: 本文の「依存: #N」、親 Issue / sub-issue、他 Issue の成果物を前提にしているか（明示と暗黙を区別）
- 規模: DoD の項目数
- ## 未確定事項: ユーザーの決定待ちと書かれた項目があれば、その言い回しを原文のまま（「要ユーザー確認」「ユーザー判断」「要確認」など）
- 着手の印: コメントに「## 着手」があれば、ブランチ名・セッション URL・日時
- 期限・リスク（データ欠損・セキュリティ・無料枠・パッチ追従など）の記述があれば原文の引用
最後に依存グラフ（「#A → #B（B は A に依存）」）と、同じファイルを触りそうな組み合わせを列挙する。合計 150 行以内。
除外: 本文の全文引用、コードブロックの転載、ユーザー情報・URL などのメタデータ。
```

### 3. 3 つに分ける

上から順に判定し、最初に当たった区分に入れる。

| 区分 | 条件 | 扱い |
|------|------|------|
| **進行中** | 紐づく Open PR、`*/#<番号>-*` のリモートブランチ、コメントの「## 着手」の印（このセッション自身のものは除く）のいずれかがある | ラベル案を出さない（変えない）。PR がマージできる状態なら「マージ」を次の行動として挙げる |
| **ルーティン向け** | `.claude/routines/weekday-issue-start.md`「2. 対象 Issue の選定」手順 1 の候補条件をすべて満たす（条件の正本はルーティン側。ここに書き写さない） | 日次ルーティンに任せられる |
| **人がいるセッション向け** | 上のどちらでもない | 理由（要判断・依存待ち #N・親 Issue）を書く。依存待ちだけが理由なら「依存が閉じればルーティン向け」と注記する |

依存先が閉じているかは、手順 1 の Open Issue 一覧に無ければ閉じていると判定してよい。

### 4. 優先度を判定する

| ラベル | 条件 |
|--------|------|
| `priority:high` | 着手できる（依存がすべて閉じている）うえで、① 後続の Open Issue を塞いでいる、または ② 本文に期限・リスク（データ欠損・セキュリティ・無料枠超過・パッチ追従など）が書かれている |
| `priority:medium` | bug（計算結果や表示が実際とずれる）。または、依存待ちだが後続を塞いでいる／リスク対策のもの |
| `priority:low` | 上のどれにも当たらない（独立した機能追加、依存の末端） |

- **要ユーザー判断が残ることは優先度を下げる理由にしない**（区分で扱う）
- high は着手できるものに限る。依存の鎖では先頭だけが high になり、それが閉じたら次が繰り上がる。鎖が進んだら回し直す
- 同じラベルの中は、塞いでいる後続の数が多い順、次に番号の小さい順に並べる
- 依存の順番とリスクの順番が食い違うとき（例: 公開前に入れたい対策が、依存の上では後ろにある）は、順位を崩さず注記に書く

### 5. 提示して確認する

```
## Issue の消化優先度（YYYY-MM-DD 時点）

### 進行中
| Issue | 状態 | 次の行動 |
|-------|------|---------|
| #N タイトル | PR #M（マージ可能）／作業中（着手の印: <ブランチ>） | マージ／待つ |

### 人がいるセッション向け
| 順 | Issue | 現在 → 案 | 理由 | 備考 |
|----|-------|-----------|------|------|
| 1 | #N タイトル | なし → high | 後続 N 件の起点、依存は解消済み | 要判断: ... |

### ルーティン向け
| 順 | Issue | 現在 → 案 | 理由 |
|----|-------|-----------|------|

### 注記
- ファイルが重なる組み合わせ（マージ順の注意）、依存とリスクの食い違い

priority ラベルを案のとおり付け替えますか？
 [Y] すべて付け替える
 [E] 一部を変える（Issue 番号と優先度を指定。「#N は変えない」も可）
 [N] 付け替えない（順位表の確認だけ）
```

- [E] の場合は修正を反映して再提示し、改めて Y/E/N を取る

### 6. ラベルを付け替える

承認された Issue のうち、現在のラベルと案が違うものだけを更新する。

- `issue_write`（method: `update`）の `labels` は **ラベル全体を置き換える**。現在のラベルから `priority:*` を除き、新しい `priority:*` を 1 つ足した配列を渡す（種別ラベルや `needs-decision` を落とさない）
- `gh` なら `gh issue edit <N> --remove-label <旧> --add-label <新>`
- 付け替えた Issue の一覧（番号・旧 → 新）を最後に示す

## 自動化しないこと

- **無人でラベルを付け替えない**。手順 5 の確認を挟む。ルーティンにも組み込まない
- **Issue 本文・コメントを書き換えない、起票しない**（分割や新規起票が要るなら `/issue-plan` を案内する）
- **進行中の Issue のラベルは変えない**
