# モデルの割り当て

Issue ごとに着手するセッションのモデルと effort を決める、判定・着手時の確認・引き継ぎの正本。`/issue-priority` と `daily-triage` がラベルを付け、`/issue-start` Phase 1 と `weekday-issue-start` が読む。ほかのファイルに書き写さない。

使うかは、リポジトリにラベル `model:opus` があるかで決まる（確かめ方は `/issue-priority`「無人実装を使うか」と同じ）。無いプロジェクトでは、判定もラベルの付与もしない。

## ラベルとモデル

| ラベル | model | effort |
|--------|-------|--------|
| `model:fable` | `fable` | `high` |
| `model:sonnet` | `sonnet` | `medium` |
| `model:opus` | `opus` | `medium` |

model と effort は既定値で、プロジェクトで変えてよい（model は `Agent` ツールの `model` 引数と同じエイリアス）。強さの順は `sonnet` < `opus` < `fable`。

## 判定

判定の前に、Issue ごとに下調べをする（検索は数回まで。読むのは当たった行の前後だけで、探索はしない）。

- 本文が挙げるファイル・関数・画面・データの名前を Grep / Glob で引き、触る箇所がどの層（ディレクトリ）に何ファイルあるかを見る
- なぞれる既存の実装（同じ形の前例）があるかを見る
- `bug` は、本文の症状から原因の行を特定できるかを見る

本文・`/issue-priority` 手順 2 の要約・下調べの結果で上から順に見て、最初に当たったラベルにする。

1. `model:fable`: 次のどれかに当たる
   - `bug` で、原因が本文に無く、下調べでも原因の行を特定できない
   - 方式・設計の選択が残り（要約の「変更内容」）、変更が複数の層（UI・API・データ・定期処理など）の構造かデータモデルに及ぶ
   - 並行処理・性能・セキュリティ・データ移行の正しさが、目的そのもの
2. `model:sonnet`: 変更箇所と方針が本文で決まっていて（要約の「変更内容」が「決まっている」）、`## 未確定事項` に決定待ちの項目が無く、下調べで本文に無い変更箇所（別の層・呼び出し元）が見つからない
3. `model:opus`: 上のどちらにも当たらない

- `model:*` が付いている Issue のラベルは変えない（人が付け替えたものを戻さないため）。変えるのは、`/issue-priority` 手順 5 の [E] で指定されたときと、「着手後の再判定」で上げるときだけ
- 進行中の Issue と、`meta` / `question` の Issue には付けない

## 着手時の確認

`/issue-start` Phase 1 手順 1 で Issue を読んだ直後に行う。次のどれかなら、何もせずに Phase 1 を続ける。

- Issue に `model:*` が無い
- 引き継がれたセッション（依頼文に「モデル振り分け済み」とある）か、`weekday-issue-start` の実行（手順 2-4 で済んでいる）。または、ユーザーがこのセッションで進めるよう言っている
- 今のセッションのモデルがラベルと一致する。モデルは、クラウドセッションなら `get_session`（引数なし）の `session_context.model`、それ以外はシステムプロンプトのモデル名で見る。ラベルの名前（`sonnet` / `opus` / `fable`）がモデル名に含まれていれば一致とし、effort の違いは見ない

一致しないときは、ラベルのモデルのセッションに引き継ぐ。

1. `create_session` が使える（クラウドセッション）なら、下の「引き継ぎ」で子セッションを立てる。ラベル・今のモデル・子セッションの URL（`https://claude.ai/code/<子セッションの ID>`）と、続きはそのセッションで行うことを伝えて、このセッションでは Issue の作業をしない（ブランチも着手の印も作らない）
2. 使えない（ローカルなど）か失敗したら、ラベルと今のモデルを 1 行で伝えて、そのまま Phase 1 を続ける

## 引き継ぎ

`create_session` を次の引数で呼ぶ。

- `model` / `effort`: 「ラベルとモデル」の表の値。`effort` が理由で拒まれたら、`effort` を外して呼び直す
- `source_url`: `get_session` の `session_context.sources` にある、このリポジトリの URL
- `outcome_branch`: Issue のブランチ名（`.claude/rules/git-conventions.md`「ブランチ命名」。type は Issue のラベルから取る）
- `title`: `#<番号> <Issue のタイトル>`
- `prompt`: 次の文面（`<...>` を埋める）

```text
Issue #<番号> を /issue-start で進めてください。

- モデル振り分け済み（ラベル `model:<名前>` により、セッション <このセッションの ID> から引き継ぎ）。モデルの確認と Phase 1 手順 0.5 はしない
- このセッションは作業ブランチが割り当てられておらず、detached HEAD で始まる。Phase 2 は「クラウドセッションの場合」ではなく通常の手順で、`origin/main` から `<ブランチ名>` を切る
```

子セッションは、このセッションの会話を引き継がない。Issue に無い指示や決定をこの会話で受けていたら、文面の箇条書きに原文のまま足す。

## 着手後の再判定

`/issue-start` Phase 3 手順 6 で探索の結果を共有したあとに行う。Issue に `model:*` が無い、今のセッションのモデルが `fable`、依頼文に「再判定済み」とある、ユーザーがこのセッションで進めるよう言っている、のどれかなら行わない。

1. 探索の結果で、「判定」の 1（`model:fable`）に当たるかを見る。当たらず、今のラベルが `model:sonnet` なら、方式・設計の選択が残ると分かったときだけ `model:opus` とする（本文に無い呼び出し元が見つかっただけでは上げない）
2. 今のラベルより強いラベルにならなければ、何もせずに進む（下げる方向には付け替えない）
3. 強ければ、Issue の `model:*` を付け替える（旧いラベルを外して新しいラベルを足す。ほかのラベルは落とさない）
4. 新しいラベルのモデルが今のセッションのモデルより強く、`create_session` が使えるなら、「引き継ぎ」で子セッションを立てる（`weekday-issue-start` の実行では「無人実行の引き継ぎ」に従う）。文面の箇条書きに次を足す
   - `再判定済み（探索の結果、ラベルを model:<旧> から上げた: <当たった項目>）。再判定はしない`
   - `Phase 1 の確認と判断は前のセッションで済み。Issue は読み直すだけにし、質問と needs-decision の判定はやり直さない`
   - 探索の要約（把握したこと・未確定のこと・スコープ外の問題の候補・重要なファイルの `file:line`。30 行以内）と、「これを Phase 3 の結果として使い、足りない所だけ読む」
   - Phase 1・3 でユーザーが決めたこと（原文のまま）
5. 子セッションを立てなかった（立てられなかった）ときは、付け替えたラベルと今のモデルを 1 行で伝えて、そのまま続ける
6. 立てたら、Phase 2 で Issue に付けた着手の印があれば見出しを「## 着手（取り下げ）」に書き換え、付け替えたラベル・当たった項目・子セッションの URL を伝えて、このセッションでは作業をやめる

## 無人実行の引き継ぎ（`weekday-issue-start`）

手順 2 で Issue を選んだあと、「着手時の確認」の 3 つ目の箇条の見方で、ラベルとこのセッションのモデルを比べる。ラベルが無いか一致すれば、そのまま手順 3 に進む。一致しなければ、「引き継ぎ」の引数で子セッションを立てる（`outcome_branch` は手順 3-1 で作るはずのブランチ名、`title` は `weekday-issue-start: #<番号> <Issue のタイトル>`）。`prompt` は次の文面にする。

```text
# weekday-issue-start（引き継ぎ）

あなたはこのリポジトリの定期ルーティン `weekday-issue-start` の続きです。モデル振り分け済み（ラベル `model:<名前>`）で、事前点検と Issue の選定は前のセッション <このセッションの ID> が終えています。

1. 作業ディレクトリのリポジトリで `git fetch origin main` を実行する
2. `git show origin/main:.claude/routines/weekday-issue-start.md` で手順書を読む。冒頭の箇条書きを読んだら、手順 1・2 は行わずに、Issue #<番号> を対象に手順 3 から最後まで実行する。手順 3-1 のブランチ名は `<ブランチ名>`
3. 手順 5 の実行報告の「Open PR 数」から「対象」までの行は、次をそのまま使う

<手順 1・2 の結果を、実行報告の「Open PR 数」から「対象」までの行の形で>
```

- 子セッションを立てられたら、このセッションは続きの手順を行わず、実行報告も投稿しない（報告は子セッションが 1 件投稿する）。引き継いだ Issue・ラベル・子セッションの ID をセッションに出して終える
- 「着手後の再判定」で上げるときも、この文面で立てる。実行報告の行は、自分が引き継がれていれば渡された行を、そうでなければ手順 1・2 の結果を渡す。文面の 2 に「ブランチは push 済みなので、手順 3-1 では作らずに `git fetch origin "<ブランチ名>:refs/remotes/origin/<ブランチ名>"` と `git switch <ブランチ名>` で使い、Phase 2 の push は行わない」を足し、末尾に再判定の手順 4 の箇条書き（ユーザーの決定を除く）を足す
- 立てられなかったら、このセッションのモデルのまま手順 3 に進み（再判定では、そのまま続きを行い）、実行報告の「モデル」の行と PR 本文の `## 実装判断（無人実行）` に、ラベル・実装したモデル・引き継げなかった理由を書く
