# Phase 5: 実装・検証・コミット

Phase 4 で承認された設計（スキップした場合は Phase 4 で述べた方針）がスコープ。`CLAUDE.md` と `.claude/rules/coding-standards.md` の規約に従って実装する。

## 検証手段を先に持つ

「動いたはず」ではなく、結果で確かめられる状態を作ってから書き始める。

1. **DoD を検証に翻訳する**: 完了条件の各項目について「どのテスト・コマンド・操作で確かめるか」を決める。`tech-stack.md` のテストコマンドを確認する
2. **振る舞いを仕様化できるなら、失敗するテストを先に書く**: バグ修正なら再現テスト、機能追加なら期待する振る舞いのテスト。実行して **失敗することを確認** してから実装に入る。既存のテストが無いリポジトリや、仕様化しにくい変更（設定・ドキュメント・探索的な変更）では無理に書かない
3. **たまにしか起きないバグは、直す前に落ちる再現条件を作る**: 負荷・タイミング・環境しだいで起きるバグ（CPU が混んだときだけタイムアウトする、など）は、普段の状態で完了条件（「N 回続けて実行して落ちない」など）を確かめても直す前から満たせてしまい、直したことが効いたかを示せない。2 のテストを書かない変更（設定の変更など）や、ずっと残すテストにできない場合でも、直す前に、落ちる条件（負荷を掛ける・回数を増やす・処理の順番やタイミングをずらす）を作業中に作る。同じ条件・同じ回数で、直す前は落ち、直した後は落ちないことを見る。そういう条件を作れなければ、完了条件を満たしていても、直したことが効いたかは未検証として報告する
4. **テストの扱い**:
   - Issue が求める振る舞い 1 つにつき、焦点の絞られたテストを 1 つ程度。作業中の確認用スクリプトを恒久的なテストファイルにしない。スキルデータ（`src/client/data/*`）を import する確認用のコードは tsx / node で直接実行すると止まるので、一時テストにして Vitest で実行し、終わったら消す。Claude Code から実行すると、通ったテストの `console.log` は既定では出ないので、値を出して見るなら `--reporter=default` を付ける（どちらも `.claude/skills/issue-start/pitfalls.md`「スキルデータを import するコードを tsx / node で直接実行すると、アイコン PNG で止まる」）
   - **既存のテストを通すために書き換えたり削除したりしない**。テストが間違っていると自分で判断したら、直さずにユーザーに報告する
   - ただし、Issue（または承認された設計）が正しい値・振る舞いを明示していて、既存のテストがその修正前の値を期待値に固定しているだけなら、期待値を Issue の値に合わせてよい。PR 本文の「変更点」に不可避の副次変更として書く。Issue が明示していない値（直した値から計算される値など）を期待値にしたテストが落ちたら、これまでどおり報告する
   - テストは正しさを確かめるためのもので、解を定義するものではない。テストだけを通す実装（特殊ケース分岐、ハードコード）はしない
   - テスト記述時は `.claude/rules/testing-conventions.md` の既知の罠（リソース上限キャップ、エラー時の倍率等）を確認する
   - Phase 4 で近似・既知の制限とした点は、その最悪の入力でもテストを 1 つ書き、設計案に書いた結果になることを確かめる。通常の入力のテストだけでは、近似の影響がレビューまで見えない

## 実装

1. 承認された設計に沿って実装する。設計から外れる必要が出たら、理由を添えて短く報告してから進める（スコープが変わるならユーザーに確認。手順書・規約から人の確認を外す・弱めることになるなら、報告で進めず、文面を示して承認を得てから当てる（`phases/04-design.md`「いつ設計 Phase を行うか」の 1 行目）。無人ルーティン（`.claude/routines/`）の書き込み・判断の手順を変えることになるなら、同じく報告で進めず、文面を示し、その変更をコミットして push する承認も同じ質問で取ってから当てる（同じ表の 2 行目））
2. **ライブラリ仕様の確認（必要な場合のみ）**: API 仕様が不明なら context7 等のドキュメント参照 MCP か公式ドキュメントで確認してから使う。既存コードの使い方に倣う
3. **過剰設計しない**: バグ修正で周辺コードを整理しない、頼まれていない設定項目・抽象化・将来対応を入れない。気になった点はスコープ外問題のメモへ
4. **進捗の共有**: 複数ファイルを読み込んだ直後や、まとまった変更を終えた節目に、把握したこと・これからの変更を 2〜4 行で報告する。報告のために回答を待つ必要はない（確認が必要な判断は明示して聞く）
5. **実装をサブエージェントに委譲する場合**（独立した領域の並列化が要るときのみ）: プロンプトに、承認された設計の該当部分と、**触ってはいけない範囲**（Issue の「やらないこと」、別 Issue に回したスコープ、他のエージェントの担当ファイル）を明記する（`.claude/rules/context-efficiency.md`「委譲時のプロンプトに含めるもの」）。統合前に `git diff --stat` で担当範囲外のファイル変更が混じっていないか確認し、混じっていれば戻す

環境依存のハマりどころ（Windows の改行コード・ヒアドキュメントのバックスラッシュ・`gh --jq` の正規表現・npm での依存更新等）の回避策は `.claude/skills/issue-start/pitfalls.md` にまとめてある。該当する環境・ツールを使うとき（`npm update` / `npm audit fix` 等で依存を更新するときを含む）だけ読む。

## コミット前の検証

各コミットの前に、関連するテスト・リント・型チェックを実行し、結果を確認する：

```bash
npm test
npx tsc --noEmit
```

- 失敗したら直してから進む。直せない失敗は原因と一緒に報告する
- 出力は要点だけ応答に残す（全文を貼らない）
- **テストが実装を検出するかを確かめる**: 境界条件・状態のリセット・優先順位のような分岐を足したら、その分岐を一時的に外すか反転させて、対応するテストが落ちることを見る。期待したエラーが別の理由で起きる、準備の段階で止まって検証したい分岐まで届かない、などで、実装を外しても通るテストになっていることがある。外す前にそのファイルを `git add <ファイル>` でステージしておくと、見終わったあと `git restore <ファイル>` で戻せて、`git diff <ファイル>` が空になることで戻ったと確かめられる。確かめたら `git restore --staged <ファイル>` でステージも外す。`git restore <ファイル>` は作業ツリーをステージの内容に戻すだけで、ステージは残る。残すと、次に別のファイルを `git add` して `git commit` したとき、このファイルも同じコミットに入る。落ちるテストが無い分岐はテストを足す。要らない分岐なら消す。挙動をライブラリやミドルウェアに任せた部分のテストには、外せる自前の分岐が無い。代わりに、テストの入力から、テスト名が条件にしている値（ヘッダ・引数など）を外して（外せない値は既定値にして）、結果が変わることを見る。条件と逆の値（拒否を確かめるテストなら、通る値）に変えて結果が変わるのを見るだけでは足りない。逆の値は、別の経路で結果を変えていることがある。外しても結果が変わらなければ、その条件が無くても同じ結果になる（別の入力だけで結果が決まっている）ので、テストはその条件を確かめていない。その値だけが違って結果も違う入力の組をテストにするか（例: 条件の値なら拒否され、その値だけを通る値にすると通る、を 1 つのテストで確かめる。条件を見ずに拒否する実装では、通る側が落ちる）、テスト名を、結果を決めている条件に合わせて直す
- **hook の所要時間を延ばしたら、登録した `timeout` と照らす**: リトライ・待ち・ネットワーク処理を hook に足したら、待ちの上限と回数から最悪の所要時間を見積もり、`.claude/settings.json` でその hook に設定した `timeout`（秒）に収まるかを確かめる。超えると Claude Code は hook を止めて出力を捨てるので、SessionStart hook ならバナーが失敗の報告ごと消え、PreToolUse hook なら検証されないままツールの呼び出しが通る（`"onFailure": "block"` を付けた hook では、逆にツールの呼び出しが止まる）。収まらなければ、hook 側の待ちを短くするか `timeout` を上げる。どちらも、設計に無い変更なら「実装」の手順 1 のとおり報告してから進める
- **md に載せたコード・コマンドは、md から抜き出して実行する**: skill・rules・docs・手順書のどれでも、コード例やコマンドを載せた md を足す・変えたら、載せたとおりに動くかを確かめる。試作したスクリプトが動いても、md に載せた版とは、書いているうちにコメント・引数・変数名がずれる。md のコードブロックを機械的に抜き出し（フェンスの行番号を `grep -n` で見て、その間を `sed -n '<開始>,<終了>p' <file>` で取る）、そのまま実行して確かめる。手で写し直さない。プレースホルダー（`<repo>` など）も `sed` で置き換える。既存のスニペットと組み合わせて使う手順は、それぞれを同じように抜き出して組み立てる。本番・リモートにしか効かないコマンド（本番のデータベースや外部サービスを操作する CLI など）は、その CLI をスタブに差し替えて回す。スタブは、リモートを指す引数をローカル相当（ローカルのデータベース・エミュレーターなど）に置き換えて本物の CLI に渡すものにし、PATH の先頭か、手順がその CLI を呼ぶ場所（プロジェクトの依存の実行ファイルの置き場所など）に置く。仮の HOME に置いたリポジトリのコピーで回す（CLI の認証情報は HOME の下にあることが多く、作業ツリーにもスタブを残さないため）。回す前に、手順どおりに呼んだ CLI がスタブに当たることを確かめる。差し替えた範囲（リモート側の権限・応答形式）は未検証として報告する

### 起動時に読まれる設定の検証

`.claude/settings.json` の hooks 登録・`.mcp.json`・SessionStart hook のように Claude Code 自身がセッション起動時に読み込む設定を変える Issue では、作業中のセッションのままでは変更後の動きを確かめられない。hook スクリプトの出力だけなら直接実行（`bash .claude/hooks/session-start-info.sh </dev/null`）で見られるが、`.mcp.json` の読み込みと SessionStart hook は起動時にしか起きない。settings.json の hooks の登録（PreToolUse など）の変更は、逆に作業中のセッションにもすぐ効く。登録するスクリプトを先に置いてから登録する（無いスクリプトを `"onFailure": "block"` で登録すると、Bash の呼び出しがすべて止まる）。どれも、新しく起動したセッションでの動きは作業中のセッションでは確かめられないので、コミット・push してから、**PR ブランチで開いた新しいセッション** で検証する：

- クラウドセッションなら、セッション作成ツール（`create_session`。`source_url` にこのリポジトリ、`source_revision` に PR ブランチを指定）で子セッションを立てるのが確実。結果は `list_events` に `kinds: ["result"]` と `limit: 100` を付けて読む（絞り込みは読み込んだあとに掛かるので、件数が少ないと `result` が入らないことがある。子セッションの返答は `result` イベントの `result` に入る。途中経過が要るときだけ `assistant` を足す。`system` は読まない。起動時の `init` イベントが 1 件で数万トークンあり、ツールとスキルの一覧と計測値だけで検証結果は入っていない）。使えなければ、ユーザーに PR ブランチで新しいセッションを開いてもらう
- ユーザーに検証を頼むときは、渡す検証プロンプトの **先頭** に次の確認を入れる。既定ブランチで起動したセッションが変更前の状態を検証して全手順が失敗する、という往復を防ぐため：

  ```
  まず `git branch --show-current` と `git rev-parse HEAD` を表示してください。ブランチが `<PR ブランチ>`、HEAD が `<コミット SHA>` でなければ、以降の手順は実行せず、表示したブランチと HEAD を報告して止まってください。
  ```

skill（`.claude/skills/<name>/` の `SKILL.md` と補助ファイル）の追加・変更はこれに当たらない。Claude Code は skill のディレクトリを監視していて、変更は作業中のセッションにそのまま読み込まれる。新しいセッションを待たずに、その場で回して検証する。手順を読むだけのレビューでは、実際に回したときに出る判定条件の漏れや出力の多さに気付きにくい。

- **Skill ツールで呼ぶ**: ラベル付与・ブランチ作成・コメント投稿・起票のような副作用のある手順は、実行せずに判定結果と出す予定の内容だけを報告するよう指示を添えて呼ぶ。編集の直後は反映が間に合わず、編集前の本文が返ることがある。読み込まれた本文に今回の変更箇所が入っているかを確かめ、無ければ skill 一覧の再通知（system reminder）が届いてから呼び直す。skill の一覧に出なければ、ユーザーに `/reload-skills` を実行してもらう（組み込みのコマンドで、Skill ツールからは呼べない。起動時に無かった skills ディレクトリは監視されないので、そこでは変更のたびに要る）
- **新しいコンテキストで空回しさせる**: 書いた本人が呼ぶと、書いたときの意図で読んでしまい、解釈が分かれる箇所に気付きにくい。判定基準や分岐を足したときなど、手順の解釈を確かめたいときは、汎用のサブエージェントに変更後のファイルをディスクから読ませ、架空の入力で空回しさせて、迷った点・解釈が分かれた点を返させる。プロンプトには、ファイルの編集・コミット・GitHub への書き込みのような副作用のある操作をしないことと、scratchpad など作業ディレクトリの外にある既存のファイルも書き換えず、試しのファイルは新しい専用のディレクトリにだけ置くことを書く（呼び出し元が検証に使っているファイルを上書きされると、本当の不一致と区別できない）。ディスクから直接読むので、上の反映の遅れも受けない。判定の文言（何を拾う・拾わないかの基準）を変えたときは、変更前の文言でも、対象の入力だけを同じように空回しして、結果が変わることを確かめる。変更後だけで期待どおりに出ても、変更の効果なのか元からそうだったのかを区別できず、LLM の判定は揺れるので、なおさら区別しにくい（「コミット前の検証」で、分岐を外して対応するテストが落ちるのを見るのと同じ考え方）。変更前の文言は `git show origin/main:<path>` を作業ディレクトリの外に書き出して読ませ、新旧は並列に回してよい。全件を回すより、対象を絞った新旧の比較の方が変更の効果を直接示せる。副作用（push・コメント・ラベル付け）を行う時点を動かす変更では、狙いの場面だけでなく、その時点より後にある途中終了の経路（判断保留で終える・Phase を省く・途中で落ちる）も場面に入れ、副作用が残した状態が次の実行の判定（選定の条件・作業中の検知など）に当たらないかを見る。狙いに沿った場面だけだと、時点が動いたことで影響を受ける別の終わり方が漏れる。情報の集め方（問い合わせ・読むもの）を変えたときは、架空のデータを最初から全部渡さず、2 回に分ける。1 回目で手順書が指示する問い合わせを列挙させ、2 回目で列挙した分の結果だけを渡して判定させる。最初から全部渡すと、収集の指示が無い文面でも渡されたデータで判定できてしまい、新旧の差が見えない。2 回目は、1 回目の列挙を添えて新しいエージェントを起動して渡す（`SendMessage` で同じエージェントに続けて渡すと、返事はバックグラウンドで届く）
- **MCP が無いときの代わりの経路を変えたら、MCP を使わない前提で回す**: その場で呼ぶと、MCP が使える環境では MCP の経路を通り、変えた代わりの経路（`gh` の REST など）は通らない。新しいコンテキストのサブエージェントに、変えたファイルはディスクから読ませ（委譲プロンプトを変えたなら、その部分だけ抜き出して渡し）、「GitHub MCP は使えない前提。MCP のツールはロードしない」と書いて回させ、実行したコマンドの一覧を返させる。Issue や PR を作るような副作用のあるコマンドは実行させず、実行するはずのコマンドとして一覧に入れさせる。一覧に MCP のツールが無く、変えた経路のコマンドだけが並ぶことを確かめる
- **サブエージェントの結果を確かめてからコミットする**: 上の 2 つでサブエージェントを起動するときは、`run_in_background: false` で同じメッセージから並列に起動し、全員の結果を受け取って確かめてからコミットする。2 分ほどで終わらないものは途中でバックグラウンドに回され、結果は後のツール呼び出しの結果に添えて届くので、それまでは残りの検証を先に進める（`.claude/skills/issue-start/pitfalls.md`「フォアグラウンドで起動したサブエージェントも、2 分ほどでバックグラウンドに回される」）。進めるものが無くなったら、ターンを終えて待つ（結果が届くとセッションが再開する）。クラウドセッションでは止まるときに環境側の Stop hook が未コミットの変更の commit / push を求めるが、従うと検証の前にコミットすることになるので、結果が出るまではコミットせず、待っている理由を書いてもう一度ターンを終える（同「クラウドセッションの Stop hook は、止まるたびに未コミットの変更の commit / push を 1 度だけ求める」）
- **md に載せたコード・コマンドを確かめる**: 「コミット前の検証」の「md に載せたコード・コマンドは、md から抜き出して実行する」のとおりに回す（skill の手順に載せたものも同じ）

## コミット粒度

- 論理的に独立した変更単位ごとにコミットする（1 コミット = 1 テーマ）
- 各コミットがビルド可能・テスト通過の状態を保つ。WIP コミットは避ける
- メッセージは `<type>: <subject> #<issue番号>`。PreToolUse hook（`.claude/hooks/validate-commit-message.sh`）が検証する（詳細は `.claude/rules/git-conventions.md`）

## 系統横断ユニットテスト（Issue #231）

Phase 4 で系統スキルの網羅性を要した設計の場合（`phases/04-design.md`「必須チェック項目」）、**系統全体に同じ仕様が適用されているか** を 1 つのテストで確かめる。UI 視覚検証（Playwright MCP）では個別スキルの動作は確認できても、「系統の一部スキルだけ反応しない」バグは見つけにくい。系統横断バグの **一次防御線はユニットテスト**。

```ts
// Vitest / Jest の例。他言語では parametrize / table-driven test に読み替える
import { test, expect } from "vitest";

const BLIZZARD_FAMILY = ["blizzard", "blizzara", "blizzaga", "blizzaja"] as const;

test.each(BLIZZARD_FAMILY)("UB 中の %s で MP が回復する", (skillId) => {
  const result = simulateCast(skillId, { ubLevel: 3 });
  expect(result.mpDelta).toBeGreaterThan(0);
});
```

- `test.each` で系統スキル ID を回して共通アサートにする。新スキル追加時も配列へ 1 行足すだけで対象になる
- 既存テスト（例: `src/client/logic/__tests__/blm-af-ub.test.ts`）に同じパターンがあれば踏襲する
- UI 検証は別途 Phase 6 で実施する

## スコープ外問題の記録と末尾提案

実装中に当該 Issue のスコープ外の問題（周辺コードのバグ／仕様乖離／技術負債等）に遭遇したら、**その場で直さずメモに留める**。

1. **メモに記録する**: 何が問題か（1〜3 行）、該当ファイルと行、バグなら再現手順
2. **Phase 5 末尾でまとめて提案する**: 実装とコミットが一通り完了したら、記録した問題を一括で提示する
   - 起票判定基準は `SKILL.md`「スコープ外問題の起票提案」
   - 重複確認・提示・起票は `SKILL.md`「起票フロー（共通）」の手順どおりに行う（本文の構成と、親の未マージの変更を前提にするときの `依存:` もそこにある）。候補ごとに確認し、承認されたものだけ起票する
3. **発見が無かった場合**: 「スコープ外問題の検出: なし」と一言添える

> 例外: 進行不能な致命バグに遭遇した場合は即座に報告し、当該 Issue のスコープを広げるか・別 Issue に切り出して先に対応するかをユーザーが判断する。

## ワークフロー改善余地のメモ（Phase 8 向け）

「この手順は冗長だった」「このガードレールがあれば楽だった」「MCP ツールのこの挙動で詰まった」のような **ワークフロー自体への気づき** は短文メモとして控え、Phase 8 で知見ボード（#195）にユーザー確認のうえ書く（`.claude/rules/workflow-feedback.md`、`phases/08-issue-recording.md`）。その場では直さない。コード上のバグは前節のスコープ外問題として扱う。
