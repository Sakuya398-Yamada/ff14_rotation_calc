# Phase 5: 実装・検証・コミット

Phase 4 で承認された設計（スキップした場合は Phase 4 で述べた方針）がスコープ。`CLAUDE.md` と `.claude/rules/coding-standards.md` の規約に従って実装する。compaction の後など、設計の細部が手元に無いときは、`phases/04-design.md` 手順 6 の設計コメントを読み直してから続ける。

## 検証手段を先に持つ

「動いたはず」ではなく、結果で確かめられる状態を作ってから書き始める。

1. **DoD を検証に翻訳する**: 完了条件の各項目について「どのテスト・コマンド・操作で確かめるか」を決める。`tech-stack.md` のテストコマンドを確認する。リポジトリの外の設定（CI・配信基盤のダッシュボードなど）を変える項目は、ビルド・デプロイの成功のステータス（変えた設定が使われずに走っても出る）ではなく、変えた設定の効果（ログに出た実行コマンドの行、期待した副作用）で確かめる形にする。設定が新しく作るリソースにだけ付くサービスがあるので、変更前からある環境（ブランチごとの環境など）でも、その環境の実行結果で確かめる
2. **振る舞いを仕様化できるなら、失敗するテストを先に書く**: バグ修正なら再現テスト、機能追加なら期待する振る舞いのテスト。実行して失敗することを確認してから実装に入る。既存のテストが無いリポジトリや、仕様化しにくい変更（設定・ドキュメント・探索的な変更）では無理に書かない
3. **たまにしか起きないバグは、直す前に落ちる再現条件を作る**: 負荷・タイミング・環境しだいで起きるバグ（CPU が混んだときだけタイムアウトする、など）は、普段の状態で完了条件（「N 回続けて実行して落ちない」など）を確かめても直す前から満たせてしまい、直したことが効いたかを示せない。2 のテストを書かない変更（設定の変更など）や、ずっと残すテストにできない場合でも、直す前に落ちる条件（負荷を掛ける・回数を増やす・処理の順番やタイミングをずらす）を作業中に作り、同じ条件・同じ回数で、直す前は落ち、直した後は落ちないことを見る。作れなければ、完了条件を満たしていても、直したことが効いたかは未検証として報告する
4. **テストの扱い**:
   - Issue が求める振る舞い 1 つにつき、焦点の絞られたテストを 1 つ程度。作業中の確認用スクリプトを恒久的なテストファイルにしない。スキルデータ（`src/client/data/*`）を import する確認用のコードは tsx / node で直接実行すると止まるので、一時テストにして Vitest で実行し、終わったら消す。Claude Code から実行すると、通ったテストの `console.log` は既定では出ないので、値を出して見るなら `--reporter=default` を付ける（どちらも `.claude/skills/issue-start/pitfalls-project.md`「スキルデータを import するコードを tsx / node で直接実行すると、アイコン PNG で止まる」）
   - **既存のテストを通すために書き換えたり削除したりしない**。テストが間違っていると自分で判断したら、直さずにユーザーに報告する
   - ただし、Issue（または承認された設計）が正しい値・振る舞いを明示していて、既存のテストがその修正前の値を期待値に固定しているだけなら、期待値を Issue の値に合わせてよい。PR 本文の「変更点」に不可避の副次変更として書く。Issue が明示していない値（直した値から計算される値など）を期待値にしたテストが落ちたら、これまでどおり報告する
   - テストは正しさを確かめるためのもので、解を定義するものではない。テストだけを通す実装（特殊ケース分岐、ハードコード）はしない
   - テスト記述時は `.claude/rules/testing-conventions.md` の既知の罠（リソース上限キャップ、エラー時の倍率等）を確認する
   - 振る舞いを変える変更では、落ちたテストに加え、変えた振る舞いをセットアップや途中の手順に含むテストを Grep で洗う。最後の結果しか assert していないテストは、途中の意味が変わっても通り続ける。途中が狙いどおりかを assert していなければ、途中の assert を足す（テストの意図を保つための追加で、期待値の書き換えではない）。並びや状態の組み合わせ（入力 A のあとに B が来る、など）の条件は、テストデータが複数行にまたがるので Grep で拾いきれない。その場合は、旧ロジックの判定を一時的に新ロジックと並べて計算させて全テストを回し、新旧の結果が食い違った箇所をテスト名付きで、リポジトリの外（scratchpad など）のファイルに書き出して洗う。値ではなく、変化が結果のどこに現れるかを動かす変更では、並べても否定・維持の確認（「X を付けない」など）の空振りは見つからない。動かした項目の読み取りを計測し（読まれたら、読んだテストの行を記録する）、そこを読む否定・維持の確認には、変化の移った先を見る assert を足す。並べる・計測するために手を入れたファイルは、「コミット前の検証」で分岐を外すときと同じく、先に `git add` しておき、見終わったら戻す
   - Phase 4 で近似・既知の制限とした点は、その最悪の入力でもテストを 1 つ書き、設計案に書いた結果になることを確かめる。通常の入力のテストだけでは、近似の影響がレビューまで見えない

## 実装

1. 承認された設計に沿って実装する。設計から外れる必要が出たら、理由を添えて短く報告してから進める。ただし、承認した設計の「変える範囲」に無い領域（ファイル・モジュール）に、不可避な副次変更（`.claude/rules/git-conventions.md`「スコープ原則（1 Issue = 1 PR）」。型定義の追従や、上の「テストの扱い」で期待値を合わせるテストなど）を超えて手を入れる必要が出たとき、スコープが変わるとき、手順書・規約から人の確認を外す・弱めるとき（`phases/04-design.md`「いつ設計 Phase を行うか」の 1 行目。書く文面を示す）は、報告で進めず、設計の更新案を示して承認を取り直す。承認を得たら `phases/04-design.md` 手順 6 の設計コメントも直す。無人ルーティン（`.claude/routines/`）の書き込み・判断の手順（ルーティンが判定基準として参照する skill の手順と、ルーティンが書き込み（起票・コメント投稿・コメント編集など）に使うコマンド例（`pitfalls-cloud.md` のフォールバック。テンプレート更新で変わる場合も同じ）を含む。取得だけのコマンド例・PR 作成の例と、`weekday-issue-start` が従う `/issue-start` の手順は除く）を変えることになるときも、報告で進めず、文面を示し、その変更をコミットして push する承認も同じ質問で取ってから当てる（同じ表の 2 行目）。無人実行では `.claude/routines/weekday-issue-start.md`「4. 実装」の表のとおり
2. **ライブラリ仕様の確認（必要な場合のみ）**: API 仕様が不明なら context7 等のドキュメント参照 MCP か公式ドキュメントで確認してから使う。既存コードの使い方に倣う
3. **過剰設計しない**: 目的と関係ない周辺コードは整理しない。目的のために要る周辺の作り直しは、承認した設計にあるものだけ行い、無ければ手順 1 のとおり設計を更新する。目的と関係ない気になった点はスコープ外問題のメモへ
4. **進捗の共有**: 複数ファイルを読み込んだ直後や、まとまった変更を終えた節目に、把握したこと・これからの変更を 2〜3 行で報告する。報告のために回答を待つ必要はない（確認が必要な判断は明示して聞く）
5. **実装をサブエージェントに委譲する場合**（独立した領域の並列化が要るときか、`.claude/rules/context-efficiency.md`「サブエージェント委譲」の「モデル」のとおり下のモデルに出すときのみ）: プロンプトに、承認された設計の該当部分と、触ってはいけない範囲（`.claude/rules/context-efficiency.md`「委譲時のプロンプトに含めるもの」の 5 と、他のエージェントの担当ファイル）を明記する。統合前に `git diff --stat` で担当範囲外のファイル変更が混じっていないか確認し、混じっていれば戻す。下のモデルに出した分は、差分を読んで設計どおりかを確かめてから統合する

環境依存のハマりどころの回避策は、テンプレート由来のものを `.claude/skills/issue-start/pitfalls.md` に、このプロジェクト固有のもの（npm での依存更新・スキルデータを import するコードの直接実行等）を `.claude/skills/issue-start/pitfalls-project.md` にまとめてある。該当する環境・ツールを使うときだけ読む（Windows で `sed -i` やスクリプトで一括置換するなら「一括置換で改行コードが LF に変わる」、スクリプトを `<<'EOF'` で書き出すなら「ヒアドキュメントでバックスラッシュが縮む」、gh の `--jq` なら「`gh --jq` の正規表現にバックスラッシュが通らない」。`npm update` / `npm audit fix` 等で依存を更新するなら `pitfalls-project.md` の npm の項目）。

## コミット前の検証

各コミットの前に、関連するテスト・リント・型チェックを実行し、結果を確認する：

```bash
npm test
npx tsc --noEmit
```

- 失敗したら直してから進む。直せない失敗は原因と一緒に報告する
- 出力は要点だけ応答に残す（全文を貼らない）
- **テストが実装を検出するかを確かめる**: 境界条件・状態のリセット・優先順位のような分岐を足したら、その分岐を一時的に外すか反転させて、対応するテストが落ちることを見る（期待したエラーが別の理由で起きる、準備の段階で止まって検証したい分岐まで届かない、などで、実装を外しても通るテストがある）。外す前にそのファイルを `git add <ファイル>` でステージしておき、見終わったら `git restore <ファイル>` で戻して `git diff <ファイル>` が空になることを確かめ、`git restore --staged <ファイル>` でステージも外す（`git restore <ファイル>` は作業ツリーをステージの内容に戻すだけでステージは残り、残すと次に別のファイルを `git add` して `git commit` したとき、このファイルも同じコミットに入る）。落ちるテストが無い分岐はテストを足し、要らない分岐なら消す。挙動をライブラリやミドルウェアに任せた部分のテストには外せる自前の分岐が無いので、代わりに、テストの入力から、テスト名が条件にしている値（ヘッダ・引数など）を外して（外せない値は既定値にして）、結果が変わることを見る。条件と逆の値（拒否を確かめるテストなら、通る値）に変えて結果が変わるのを見るだけでは足りない（逆の値は、別の経路で結果を変えていることがある）。外しても結果が変わらなければ、結果は別の入力だけで決まっていて、テストはその条件を確かめていない。その値だけが違って結果も違う入力の組をテストにするか（例: 条件の値なら拒否され、その値だけを通る値にすると通る、を 1 つのテストで確かめる。条件を見ずに拒否する実装では、通る側が落ちる）、テスト名を、結果を決めている条件に合わせて直す
- **hook の所要時間を延ばしたら、登録した `timeout` と照らす**: リトライ・待ち・ネットワーク処理を hook に足したら、待ちの上限と回数から最悪の所要時間を見積もり、`.claude/settings.json` でその hook に設定した `timeout`（秒）に収まるかを確かめる。超えると Claude Code は hook を止めて出力を捨てるので、SessionStart hook ならバナーが失敗の報告ごと消え、PreToolUse hook なら検証されないままツールの呼び出しが通る（`"onFailure": "block"` を付けた hook では、逆にツールの呼び出しが止まる）。収まらなければ、hook 側の待ちを短くするか `timeout` を上げる。どちらも、設計に無い変更なら「実装」の手順 1 のとおり報告してから進める
- **md に載せたコード・コマンドは、md から抜き出して実行する**: skill・rules・docs・手順書のどれでも、コード例やコマンドを載せた md を足す・変えたら、載せたとおりに動くかを確かめる。試作したスクリプトが動いても、md に載せた版とは書いているうちにコメント・引数・変数名がずれるので、md のコードブロックを機械的に抜き出し（フェンスの行番号を `grep -n` で見て、どのフェンスかは番号ではなく直前の見出し・説明文で選び、その間を `sed -n '<開始>,<終了>p' <file>` で取る）、手で写し直さずにそのまま実行する。抜き出しと実行は別の呼び出しに分け（まとめると中身を見る前に書き込みが走る）、抜き出した中身が書き込み（`gh api -X POST` / `PATCH` / `DELETE`、コメントの投稿、ラベルの付け替え、push など）を含まないかを見てから実行する。書き込みを含むものは、下のスタブの手順で回す（GitHub の API のようにローカル相当が無いものは、引数を記録して決めた応答を返すだけのスタブにする）。抜き出したものは、手順書が想定する起動のしかたと呼び出しの単位のまま回す。フェンスの一部（`node -e '…'` の中身など）だけを取り出して別の起動方法で回したり、Bash ツールの別々の呼び出しで打つ前提の行（`run_in_background` で起動する行、作業ディレクトリの外へ `cd` した次の行など）を 1 つのスクリプトにまとめたりすると、エラー無しで結果が変わることがある（作業ディレクトリの外への `cd` は次の呼び出しに残らないので、まとめると、辿ると別のディレクトリで動く手順でも通ってしまう）。プレースホルダー（`<repo>` など）も `sed` で置き換え、既存のスニペットと組み合わせて使う手順は、それぞれを同じように抜き出して組み立てる。一時リポジトリで git の挙動を確かめるときは、`.claude/skills/issue-start/pitfalls.md`「一時リポジトリで git を試すと、検証 hook がコマンド文字列に反応して止める」のとおりスクリプトファイルで回す。本番・リモートにしか効かないコマンド（本番のデータベースや外部サービスを操作する CLI など）は、リモートを指す引数をローカル相当（ローカルのデータベース・エミュレーターなど）に置き換えて本物の CLI に渡すスタブに差し替え、PATH の先頭か、手順がその CLI を呼ぶ場所（プロジェクトの依存の実行ファイルの置き場所など）に置いて、仮の HOME に置いたリポジトリのコピーで回す。回す前に、手順どおりに呼んだ CLI がスタブに当たることを確かめ、差し替えた範囲（リモート側の権限・応答形式）は未検証として報告する。コードでなく本文（文章）が判定に使うと名指ししたフィールド・値も、その手順書が既定とする取得経路（MCP が優先なら MCP のツール）で 1 回呼んで、返るかを確かめる。同じ MCP でもツールで返すフィールドが違う（`sub_issues_summary` は `issue_read` の get では返るが、`list_issues` では返らない）。返らなければ、取り方を手順書に書く

### 起動時に読まれる設定の検証

`.claude/settings.json` の hooks 登録・`.mcp.json`・SessionStart hook のように Claude Code 自身がセッション起動時に読み込む設定を変える Issue では、作業中のセッションのままでは変更後の動きを確かめられないことがある。`phases/05-startup-config-check.md` の手順で検証する。

skill（`.claude/skills/<name>/` の `SKILL.md` と補助ファイル）の追加・変更はこれに当たらない。Claude Code は skill のディレクトリを監視していて、変更は作業中のセッションにそのまま読み込まれる。新しいセッションを待たずに、その場で回して検証する。手順を読むだけのレビューでは、実際に回したときに出る判定条件の漏れや出力の多さに気付きにくい。

- **Skill ツールで呼ぶ**: ラベル付与・ブランチ作成・コメント投稿・起票のような副作用のある手順は、実行せずに判定結果と出す予定の内容だけを報告するよう指示を添えて呼ぶ。編集の直後は反映が間に合わず、編集前の本文が返ることがある。読み込まれた本文に今回の変更箇所が入っているかを確かめ、無ければ skill 一覧の再通知（system reminder）が届いてから呼び直す。skill の一覧に出なければ、ユーザーに `/reload-skills` を実行してもらう（組み込みのコマンドで、Skill ツールからは呼べない。起動時に無かった skills ディレクトリは監視されないので、そこでは変更のたびに要る）
- **新しいコンテキストで空回しさせる**: 書いた本人が呼ぶと、書いたときの意図で読んでしまい、解釈が分かれる箇所に気付きにくい。判定基準や分岐を足したときなど、手順の解釈を確かめたいときは、汎用のサブエージェントに変更後のファイルをディスクから読ませ（上の反映の遅れを受けない）、架空の入力で空回しさせて、迷った点・解釈が分かれた点を返させる。Phase 4 手順 4 で承認の前に案の文面をインラインで渡して回した結果は、編集後のファイルの該当箇所が渡した文面とバイト単位で一致すれば（`cmp`）流用してよい。プロンプトには、ファイルの編集・コミット・GitHub への書き込みのような副作用のある操作をしないことと、scratchpad など作業ディレクトリの外にある既存のファイルも書き換えず、試しのファイルは新しい専用のディレクトリにだけ置くことを書く。判定の文言（何を拾う・拾わないかの基準）を変えたときは、変更前の文言でも、対象の入力だけを同じように空回しして、結果が変わることを確かめる。変更後だけでは、変更の効果か元からそうだったかを区別できない（LLM の判定は揺れるので、なおさら）。変更前の文言は `git show origin/main:<path>` を作業ディレクトリの外に書き出して読ませ、新旧は並列に回してよい。全件より、対象を絞った新旧の比較の方が効果を直接示せる。副作用（push・コメント・ラベル付け）を行う時点を動かす変更では、狙いの場面だけでなく、その時点より後にある途中終了の経路（判断保留で終える・Phase を省く・途中で落ちる）も場面に入れ、副作用が残した状態が次の実行の判定（選定の条件・作業中の検知など）に当たらないかを見る。情報の集め方（問い合わせ・読むもの）を変えたときは、架空のデータを最初から全部渡さず（全部渡すと、収集の指示が無い文面でも渡されたデータで判定できてしまい、新旧の差が見えない）、2 回に分ける。1 回目で手順書が指示する問い合わせを列挙させ、2 回目は、1 回目の列挙を添えて新しく起動したエージェントに、列挙した分の結果だけを渡して判定させる（`SendMessage` で同じエージェントに続けて渡すと、返事はバックグラウンドで届く）
  - **文言に例を書いたとき**: 架空データには、例と同じ言い回しの入力だけでなく、言い回しと題材を変えた入力も入れる。例とほぼ同じ文の入力で迷わないのは、照合で決まっただけのことがある。文面を直して例を足したら、次の回はその例とも違う言い回しの入力を足す（入れ替えずに足すのは、前の回と同じ入力で出力を比べるため）
  - **例外・除外を足す変更**: 対象の入力だけでなく、例外の対象外（扱いが変わらないはずのもの）の入力も 1 件入れて新旧で比べる。例外を足すと、元のルールの読み方を逆算させて、対象外の扱いまで変わることがある。変わったら、回数を増やして LLM の揺れか変更の影響かを切り分ける
  - **変更前でも結論が同じだったとき**: 変更前の文言の検証役が挙げた迷い（「文面どおりなら別の値になる」など）が、変更後に消えたかで効果を示し、その旨を PR 本文の「## テスト」に書く。迷いも挙がらなければ、変更が要らない可能性をユーザーに伝える
  - **回し直しの打ち切り**: 迷った点を消すために文言を足して回し直すのは、同じ入力に対する判定の出力が前の回から変わるあいだだけにする。出力が前の回と同じで、残った迷いが表記の細部だけなら、それ以上文言を足さず、残った迷いを PR 本文の「## テスト」に書いて進む
  - **変更前の文面でも挙がる迷い**: 新旧どちらの文面でも挙がる迷い（変更の外にある既存の曖昧さ）は、起票せず、PR 本文の「## テスト」に書く。起票するのは、その曖昧さで実際の入力に誤った結果が出たものだけ（スコープ外の問題として）。この Issue で書き換えた文の中の迷いは、この Issue で直す
- **MCP が無いときの代わりの経路を変えたら、MCP を使わない前提で回す**: その場で呼ぶと、MCP が使える環境では MCP の経路を通り、変えた代わりの経路（`gh` の REST など）は通らない。新しいコンテキストのサブエージェントに、変えたファイルはディスクから読ませ（委譲プロンプトを変えたなら、その部分だけ抜き出して渡し）、「GitHub MCP は使えない前提。MCP のツールはロードしない」と書いて回させ、実行したコマンドの一覧を返させる。Issue や PR を作るような副作用のあるコマンドは実行させず、実行するはずのコマンドとして一覧に入れさせる。一覧に MCP のツールが無く、変えた経路のコマンドだけが並ぶことを確かめる
- **サブエージェントの結果を確かめてからコミットする**: 上の 2 つでサブエージェントを起動するときは、`run_in_background: false` で同じメッセージから並列に起動し、全員の結果を受け取って確かめてからコミットする。クラウドセッションでは、2 分ほどで終わらないものはバックグラウンドに回され、止まるときに環境側の Stop hook が commit / push を求めるが、結果が出るまではコミットしない。待つあいだの進め方は `.claude/skills/issue-start/pitfalls-cloud.md`「フォアグラウンドで起動したサブエージェントも、2 分ほどでバックグラウンドに回される」と同「クラウドセッションの Stop hook は、止まるたびに未コミットの変更の commit / push を 1 度だけ求める」のとおり
- **md に載せたコード・コマンドを確かめる**: 「コミット前の検証」の「md に載せたコード・コマンドは、md から抜き出して実行する」のとおりに回す

## コミット粒度

- 論理的に独立した変更単位ごとにコミットする（1 コミット = 1 テーマ）
- 各コミットがビルド可能・テスト通過の状態を保つ。WIP コミットは避ける

## 系統横断ユニットテスト（Issue #231）

Phase 4 で系統スキルの網羅性を要した設計の場合（`phases/04-design.md`「必須チェック項目」）、系統全体に同じ仕様が適用されているかを 1 つのテストで確かめる。UI 視覚検証（Playwright MCP）では個別スキルの動作は確認できても、「系統の一部スキルだけ反応しない」バグは見つけにくい。系統横断バグの一次防御線はユニットテスト。

```ts
// Vitest / Jest の例。他言語では parametrize / table-driven test に読み替える
import { test, expect } from "vitest";

const BLIZZARD_FAMILY = ["blizzard", "blizzard-2", "blizzard-3", "blizzard-4", "high-blizzard-2"] as const;

test.each(BLIZZARD_FAMILY)("UB 中の %s で MP が回復する", (skillId) => {
  const result = simulateCast(skillId, { ubLevel: 3 }); // simulateCast は説明用の仮の関数
  expect(result.mpDelta).toBeGreaterThan(0);
});
```

- `test.each` で系統スキル ID を回して共通アサートにする
- 既存テスト（例: 範囲スキルの減衰を `it.each` で回している `src/client/logic/__tests__/blm-aoe-data.test.ts`）に同じパターンがあれば踏襲する
- UI 検証は別途 Phase 6 で実施する

## スコープ外問題の記録と末尾提案

実装中に当該 Issue の目的と関係ない問題（スコープ外の問題。周辺コードのバグ／仕様乖離／技術負債等）に遭遇したら、その場で直さずメモに留める。目的のために要る修正なら、「実装」手順 1・3 のとおり設計に含める。

1. **メモに記録する**: 何が問題か（1〜3 行）、該当ファイルと行、バグなら再現手順
2. **Phase 5 末尾でまとめて提案する**: 実装とコミットが一通り完了したら、記録した問題を一括で提示する
   - 起票判定基準は `SKILL.md`「スコープ外問題の起票提案」
   - 重複確認・提示・起票は `SKILL.md`「起票フロー（共通）」の手順どおりに行う
3. **発見が無かった場合**: 「スコープ外問題の検出: なし」と一言添える

> 例外: 進行不能な致命バグに遭遇した場合は即座に報告し、当該 Issue のスコープを広げるか・別 Issue に切り出して先に対応するかをユーザーが判断する。
