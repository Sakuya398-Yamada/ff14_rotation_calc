# Phase 5: 実装・検証・コミット

Phase 4 で承認された設計（スキップした場合は Phase 4 で述べた方針）がスコープ。`CLAUDE.md` と `.claude/rules/coding-standards.md` の規約に従って実装する。

## 検証手段を先に持つ

「動いたはず」ではなく、結果で確かめられる状態を作ってから書き始める。

1. **DoD を検証に翻訳する**: 完了条件の各項目について「どのテスト・コマンド・操作で確かめるか」を決める。`tech-stack.md` のテストコマンドを確認する
2. **振る舞いを仕様化できるなら、失敗するテストを先に書く**: バグ修正なら再現テスト、機能追加なら期待する振る舞いのテスト。実行して **失敗することを確認** してから実装に入る。既存のテストが無いリポジトリや、仕様化しにくい変更（設定・ドキュメント・探索的な変更）では無理に書かない
3. **テストの扱い**:
   - Issue が求める振る舞い 1 つにつき、焦点の絞られたテストを 1 つ程度。作業中の確認用スクリプトを恒久的なテストファイルにしない
   - **既存のテストを通すために書き換えたり削除したりしない**。テストが間違っていると判断したら、直さずにユーザーに報告する
   - テストは正しさを確かめるためのもので、解を定義するものではない。テストだけを通す実装（特殊ケース分岐、ハードコード）はしない
   - テスト記述時は `.claude/rules/testing-conventions.md` の既知の罠（リソース上限キャップ、エラー時の倍率等）を確認する

## 実装

1. 承認された設計に沿って実装する。設計から外れる必要が出たら、理由を添えて短く報告してから進める（スコープが変わるならユーザーに確認）
2. **ライブラリ仕様の確認（必要な場合のみ）**: API 仕様が不明なら context7 等のドキュメント参照 MCP か公式ドキュメントで確認してから使う。既存コードの使い方に倣う
3. **過剰設計しない**: バグ修正で周辺コードを整理しない、頼まれていない設定項目・抽象化・将来対応を入れない。気になった点はスコープ外問題のメモへ
4. **進捗の共有**: 複数ファイルを読み込んだ直後や、まとまった変更を終えた節目に、把握したこと・これからの変更を 2〜4 行で報告する。報告のために回答を待つ必要はない（確認が必要な判断は明示して聞く）
5. **実装をサブエージェントに委譲する場合**（独立した領域の並列化が要るときのみ）: プロンプトに、承認された設計の該当部分と、**触ってはいけない範囲**（Issue の「やらないこと」、別 Issue に回したスコープ、他のエージェントの担当ファイル）を明記する（`.claude/rules/context-efficiency.md`「委譲時のプロンプトに含めるもの」）。統合前に `git diff --stat` で担当範囲外のファイル変更が混じっていないか確認し、混じっていれば戻す

環境依存のハマりどころ（Windows の改行コード・ヒアドキュメントのバックスラッシュ・gojq のエスケープ・バックグラウンドのプロセスの止め方等）の回避策は `.claude/skills/issue-start/pitfalls.md` にまとめてある。該当する環境・ツールを使うときだけ読む。

## コミット前の検証

各コミットの前に、関連するテスト・リント・型チェックを実行し、結果を確認する：

```bash
npm test
npx tsc --noEmit
```

- 失敗したら直してから進む。直せない失敗は原因と一緒に報告する
- 出力は要点だけ応答に残す（全文を貼らない）
- **テストが実装を検出するかを確かめる**: 境界条件・状態のリセット・優先順位のような分岐を足したら、その分岐を一時的に外すか反転させて、対応するテストが落ちることを見る。期待したエラーが別の理由で起きる、準備の段階で止まって検証したい分岐まで届かない、などで、実装を外しても通るテストになっていることがある。外す前にそのファイルを `git add <ファイル>` でステージしておくと、見終わったあと `git restore <ファイル>` で戻せて、`git diff` が空になることで戻ったと確かめられる。落ちるテストが無い分岐はテストを足す。要らない分岐なら消す

### 起動時に読まれる設定の検証

`.claude/settings.json` の hooks 登録・`.mcp.json`・SessionStart hook のように Claude Code 自身がセッション起動時に読み込む設定を変える Issue では、作業中のセッションのままでは変更後の動きを確かめられない。hook スクリプトの出力だけなら直接実行（`bash .claude/hooks/session-start-info.sh </dev/null`）で見られるが、settings.json の登録や `.mcp.json` の読み込みは起動時にしか起きない。コミット・push してから、**PR ブランチで開いた新しいセッション** で検証する：

- クラウドセッションなら、セッション作成ツール（`create_session`。`source_url` にこのリポジトリ、`source_revision` に PR ブランチを指定）で子セッションを立てるのが確実。結果は `list_events` で読む。使えなければ、ユーザーに PR ブランチで新しいセッションを開いてもらう
- ユーザーに検証を頼むときは、渡す検証プロンプトの **先頭** に次の確認を入れる。既定ブランチで起動したセッションが変更前の状態を検証して全手順が失敗する、という往復を防ぐため：

  ```
  まず `git branch --show-current` と `git rev-parse HEAD` を表示してください。ブランチが `<PR ブランチ>`、HEAD が `<コミット SHA>` でなければ、以降の手順は実行せず、表示したブランチと HEAD を報告して止まってください。
  ```

skill（`.claude/skills/<name>/` の `SKILL.md` と補助ファイル）の追加・変更はこれに当たらない。Claude Code は skill のディレクトリを監視していて、変更は作業中のセッションにそのまま読み込まれる。新しいセッションを待たずに、その場で Skill ツールで呼んで検証する。手順を読むだけのレビューでは、実際に回したときに出る判定条件の漏れや出力の多さに気付きにくい。ラベル付与・ブランチ作成・コメント投稿・起票のような副作用のある手順は、実行せずに判定結果と出す予定の内容だけを報告するよう指示を添えて呼ぶ。skill の一覧に出なければ、ユーザーに `/reload-skills` を実行してもらう（組み込みのコマンドで、Skill ツールからは呼べない。起動時に無かった skills ディレクトリは監視されないので、そこでは変更のたびに要る）。

## コミット粒度

- 論理的に独立した変更単位ごとにコミットする（1 コミット = 1 テーマ）
- 各コミットがビルド可能・テスト通過の状態を保つ。WIP コミットは避ける
- メッセージは `<type>: <subject> #<issue番号>`。PreToolUse hook（`.claude/hooks/validate-commit-message.sh`）が検証する（詳細は `.claude/rules/git-conventions.md`）

## 系統横断ユニットテスト（Issue #231）

Phase 4 で系統スキルの網羅性を要した設計の場合（`phases/04-design.md`「必須チェック項目」）、**系統全体に同じ仕様が適用されているか** を 1 つのテストで確かめる。UI 視覚検証（Playwright MCP）では個別スキルの動作は確認できても、「系統の一部スキルだけ反応しない」バグは見つけにくい。系統横断バグの **一次防御線はユニットテスト**。

```ts
// Vitest / Jest の例。他言語では parametrize / table-driven test に読み替える
import { test, expect } from "vitest";

const BLIZZARD_FAMILY = ["blizzard", "blizzara", "blizzaga", "blizzaja"] as const;

test.each(BLIZZARD_FAMILY)("UB 中の %s で MP が回復する", (skillId) => {
  const result = simulateCast(skillId, { ubLevel: 3 });
  expect(result.mpDelta).toBeGreaterThan(0);
});
```

- `test.each` で系統スキル ID を回して共通アサートにする。新スキル追加時も配列へ 1 行足すだけで対象になる
- 既存テスト（例: `src/client/logic/__tests__/blm-af-ub.test.ts`）に同じパターンがあれば踏襲する
- UI 検証は別途 Phase 6 で実施する

## スコープ外問題の記録と末尾提案

実装中に当該 Issue のスコープ外の問題（周辺コードのバグ／仕様乖離／技術負債等）に遭遇したら、**その場で直さずメモに留める**。

1. **メモに記録する**: 何が問題か（1〜3 行）、該当ファイルと行、バグなら再現手順
2. **Phase 5 末尾でまとめて提案する**: 実装とコミットが一通り完了したら、記録した問題を一括で提示する
   - 起票判定基準は `SKILL.md`「スコープ外問題の起票提案」
   - `search_issues` で重複を確認してから提案する
   - 候補ごとに Y/E/N を確認し、承認されたものだけ `issue_write`（method: `create`、`parent_issue_number` に当該 Issue）で sub-issue として起票する。sub-issue として紐づけられない場合の代替として、本文末尾に `親Issue: #<親番号>` を明記する
3. **発見が無かった場合**: 「スコープ外問題の検出: なし」と一言添える

> 例外: 進行不能な致命バグに遭遇した場合は即座に報告し、当該 Issue のスコープを広げるか・別 Issue に切り出して先に対応するかをユーザーが判断する。

## ワークフロー改善余地のメモ（Phase 8 向け）

「この手順は冗長だった」「このガードレールがあれば楽だった」「MCP ツールのこの挙動で詰まった」のような **ワークフロー自体への気づき** は短文メモとして控え、Phase 8 で知見ボード（#195）にユーザー確認のうえ書く（`.claude/rules/workflow-feedback.md`、`phases/08-issue-recording.md`）。その場では直さない。コード上のバグは前節のスコープ外問題として扱う。
