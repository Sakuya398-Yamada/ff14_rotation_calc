# Phase 1 補助: リポジトリへの変更が出ない Issue（調査・GitHub 上の操作だけ）

`phases/01-issue-analysis.md`「リポジトリへの変更が出ない Issue（調査・GitHub 上の操作だけ）」から読む。テンプレート元では `phases/01-issue-analysis.md` の同じ見出しの節にある。

リポジトリのファイルを変えずに終わる Issue の分岐。次の 2 種類がある。Phase 2〜7 はコードの変更と PR を前提にしているので、変更が出ないのに空のブランチを切ったり、根拠無く Phase を飛ばしたりしない。

- **調査だけの Issue**: 目的が調査そのもの（裏取り・原因調査・要否の判断）で、結論しだいでは変更が出ない
- **GitHub 上の操作だけで終わる Issue**: Issue 本文の書き換え・ラベルの付け替え・マージ済みブランチの削除のような GitHub 上の操作そのものが成果物で、最初から PR を作らない

## 調査だけの Issue

1. Phase 1 のあと、ブランチを切らずに調査する。読む範囲が広ければ Phase 3 と同じくサブエージェント（`code-explorer`）に任せてよい
2. 結論に応じて進め方を決める

   | 結論 | 進め方 |
   |------|--------|
   | このリポジトリへの変更が要る | 通常フローに戻り、Phase 2 からブランチを切って進める |
   | 別の Issue で直すべき問題が見つかった | `SKILL.md`「スコープ外問題の起票提案」の起票フローで sub-issue として起票し、Phase 2〜7 を省略して Phase 8 へ |
   | 変更も起票も要らない | Phase 2〜7 を省略して Phase 8 へ |

3. Phase 8 では、個別 Issue への記録（`phases/08-issue-recording.md` の 1〜4）に代えて **結論**（調べ方・結果・判断とその根拠）を Issue にコメントする。知見ボード（5）と還元（6）は通常どおり行う。起票した Issue があれば同じコメントに一覧を書く
4. 結論をユーザーに示し、確認を得てから Issue をクローズする（GitHub MCP の `issue_write`（method: `update`、`state: closed`、`state_reason: completed`）。`gh issue close <N> --reason completed` でも可（クラウドセッションでは REST。`SKILL.md`「全体ルール」の「GitHub 操作」））。PR が無いので `closes #N` での自動クローズは起きない

## GitHub 上の操作だけで終わる Issue

1. ブランチは切らず、Phase 2〜7 を省略する。Phase 5 の代わりに、次の 2・3 で操作する。途中でリポジトリのファイルの変更も要ると分かったら、通常フローに戻り Phase 2 から進める
2. **適用の前に、対象と変更内容を dry-run で出す**: 書き換える Issue 本文なら新旧の差分を、付け替えるラベルや削除するブランチなら対象の一覧を、適用せずに作る。それをユーザーに示し、確認を得てから適用する。対象は Issue を起票したときから変わっていることがあり、ブランチの削除のように戻せない操作もあるため。権限やセッションの制約で拒まれる操作は、回避を探さず、実行するコマンドを示してユーザーに頼む。クラウドの実行環境では、リモートのブランチの削除は拒まれると分かっているので、試さずにコマンドを示す（`.claude/skills/issue-start/pitfalls.md`「クラウドセッションの git プロキシは、別ブランチへの push を通し、ブランチの削除を通さない」）
   - **適用するときは、dry-run の時点の状態を前提にしない**: 確認を待つ間や、ユーザーにコマンドを流してもらうまでの間に、対象が変わることがある（残す側だった PR がマージされる、消す対象が増える、本文が書き換えられる）。自分で適用するなら、直前に対象を取り直して dry-run と同じかを見て、違えば差を示して確認し直す。ユーザーに頼むコマンドは、確認を得た対象のうち、実行するときにも条件（Open PR が無い・マージ済み など）に当たるものだけを操作する形にする（ブランチ名を `gh api` の URL に直書きすると、`#` から先が切れて別の問い合わせになる。クエリは `-X GET -f head=<owner>:<ブランチ>` のように渡す）。対象を足す方向には判定し直さない（増えた対象は確認を得ていない）。ブランチの削除では、そのうえで dry-run で見た先端の SHA を期待値にして、先端が変わっていれば `stale info` で拒まれるようにする。期待値だけでは、先端を変えずに PR が開かれた場合を止められない。SHA は 40 桁で書く（手元にそのコミットが無いクローンでは、短縮形は `cannot parse expected object name` で止まる）：

     ```bash
     git push --force-with-lease=refs/heads/<ブランチ>:<dry-run で見た SHA> origin --delete <ブランチ>
     ```
3. **適用したら取り直して確かめる**: 本文は取り直して送った内容と比べ、ブランチは `git ls-remote --heads origin` で消えたことを見る。取り直した結果が dry-run と違えば（増えた・消えた対象、実行時に条件から外れて残した対象）、その差と理由を手順 4 の操作の記録に書く。増えた対象も操作するなら、改めて dry-run を示して確認を得る。Claude Code のクラウドセッションで `gh api` から本文を編集すると、末尾に署名フッターが付いて一致しなくなる（`.claude/skills/issue-start/pitfalls.md`「クラウドセッションで `gh api` から本文やコメントを書き込むと、署名フッターが末尾に付く」）
4. Phase 8 では、個別 Issue への記録（1〜4）に代えて **操作の記録**（対象・操作の前後・dry-run との差・確かめた方法と範囲）を Issue にコメントする。知見ボード（5）と還元（6）は通常どおり行う。クローズは、上の「調査だけの Issue」手順 4 と同じく確認を得てから行う
