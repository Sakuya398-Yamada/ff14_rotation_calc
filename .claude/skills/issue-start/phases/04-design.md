# Phase 4: 設計（code-architect）とユーザー承認

**目的**: 実装に入る前にアプローチをユーザーと合意する。設計の合意が手戻りを防ぐ。設計承認はこのワークフローで最も重要な確認ポイントで、承認された設計が Phase 5 のスコープになる。

## いつ設計 Phase を行うか

| 状況 | 動き |
|------|------|
| `.claude/` の手順書・規約（skills・rules・agents）や `CLAUDE.md` から、人への確認を外す・弱める変更 | 差分を 1 文で説明できても Phase 4 を省かない。書く文面を示して承認を得てから Phase 5 で編集する。確認を外すかどうかはユーザーが決めること。auto mode では、文面の承認が会話に無いとその Edit が止められることもある（理由は表示されない） |
| 無人ルーティン（`.claude/routines/`）の書き込み・判断の手順を変える変更。ルーティンの手順書が判定基準として参照する skill（`/issue-priority` とその補助ファイル）の手順を変える変更も含む（例: `daily-triage` が `priority:*` を付けるときに使う `/issue-priority` 手順 4）。ルーティンが書き込み（起票・コメント投稿・コメント編集など）に使うコマンド例（`pitfalls-cloud.md` のフォールバック。`.claude/skills/issue-start/pitfalls-cloud.md`「クラウドセッションでは gh の GraphQL 系が使えない」）を変える変更も含む。テンプレート更新でその例が変わる場合も同じ。取得だけのコマンド例と、PR 作成の例（`weekday-issue-start` が `/issue-start` の手順で使う）は含めない。`weekday-issue-start` が従う `/issue-start` の手順は、成果物の PR を人がレビューしてからマージするので含めない | 差分を 1 文で説明できても Phase 4 を省かない。書く文面を示し、その変更をコミットして push する承認も同じ質問で取ってから Phase 5 で編集する。auto mode では、文面の承認が会話に無いとその Edit が、文面だけの承認ではその `git commit` が、分類器に止められることがある（#586 では `[Instruction Poisoning]`） |
| 差分を 1 文で説明できる（1〜2 ファイルの明確な修正、Issue に実装方針が書いてある） | Phase 4 をスキップし、方針と触るファイルを 1〜2 行で述べて Phase 5 へ（述べたファイルを「変える範囲」とみなす） |
| 複数ファイルに跨る／馴染みのない領域／アプローチに迷いがある | 自分で推奨案を組み立て（足りなければ Phase 3 に戻って読む）、ユーザーに提示して承認を得る。`code-architect` は起動しない |
| 設計の方向性自体に選択肢がある（最小変更か、構造を直すか） | 観点を変えて 2〜3 個並列に起動し、比較して推奨案を示す |

Phase 3 の探索結果に、案ごとの変更箇所と影響範囲（挙動が変わる箇所・他の機能への影響・関係する既存テスト）が根拠付きで揃っているときは、上の表で起動する場面でも `code-architect` を起動せず、その結果から設計案を組み立てて提示してよい。同じ比較をやり直しても情報は増えない。提示には、起動を省いたことと、根拠にした探索結果を書く。設計承認は省かない

Claude Code の plan mode で作業しているときは、設計案の提示と承認を `ExitPlanMode` の承認フローに乗せてよい（承認後に Phase 5 の編集が解禁される）。

## 実行手順

1. 起動数表で起動するとき（設計の方向性に選択肢があるとき）は、Phase 3 の探索結果を踏まえ、`Agent` ツールで `subagent_type: "code-architect"` を起動する。起動しないときは、自分で設計案を組み立てて手順 4 に進む
2. 複数起動するときは観点を分ける：
   - **最小変更**: 「既存コードへの変更を最小限にし、最大限再利用するアプローチで設計して」
   - **クリーン設計**: 「保守性・テスタビリティを重視した構造で設計して」
   - **実用的バランス**: 「実装速度とコード品質のバランスを取るアプローチで設計して」
3. 各プロンプトに Issue の要件・DoD・Phase 3 で分かった重要ファイル・返却量の上限を含める
4. 結果を比較し、推奨案を理由付きでユーザーに提示する。足す変更が既存の重複を増やす（同じ処理の n か所目を足す）・つぎはぎを重ねるときは、その箇所の重複の統合や作り直しは明らかに要る変更に当たるので、推奨案に含めて「変える範囲」に理由と一緒に書く。統合では各箇所の今の挙動を変えない（箇所ごとに挙動が食い違っていたら、揃えずにそのまま残し、スコープ外として起票する）。設計の中に、ドメインや業務の仕様で決まる境界条件（「ちょうど」を含むか、同時刻の処理の順番など）があるなら、推奨と一緒に設計承認に同梱せず、仕様の質問として別の質問にする（`SKILL.md`「全体ルール」の「確認の聞き方」）。答えで設計が変わらないなら設計承認と一緒に別の質問として聞き、答えで設計が変わるなら設計案を出す前に聞く。選択肢ごとに結果の違いを添え、推奨の根拠が内部のモデルとの整合だけなら、そう書く。設計の承認とまとめると、推奨の根拠に引っ張られ、実際の仕様を問う機会にならない。文面そのものが成果物で、空回し（Phase 5「新しいコンテキストで空回しさせる」）で確かめる変更（手順書・skill・rules の文面、無人ルーティンが書き込む文面など）は、編集の前に、案の文面をプロンプトにインラインで渡して新旧を空回しし、その結果を推奨に添える。承認のあとの空回しで想定外の読まれ方が見つかると、文面を変えて承認を取り直すことになる
5. **ユーザーの承認を得てから** Phase 5 に進む。承認までは作業ツリーを変えない（依存の追加や試作のコードも含む）。設計案は本文で示し、試作が要るならリポジトリの外（scratchpad 等）で行う。リポジトリ全体のコピー（`git archive`・`cp -r` など）は、クラウドセッションの auto mode で止められることがあるので、確かめたい部分だけを scratchpad の新しいディレクトリで再現する（要るライブラリだけを入れて型検査や小さなスクリプトを回す、など）。リポジトリ全体が要る確認（ビルド設定が効くかなど）は試作せず、設計案に「Phase 5 で確かめる。効かなければ <代わりの手>」と書いておく（Phase 5 で効かなかったときに、承認を取り直さずに代わりの手に移れる）。作業ツリーで試してしまったら、止まる前に `git stash push -u -m "design-trial"` で退避する（`-u` が無いと新規ファイルが残る）。承認されたら `git stash pop`、却下なら `git stash drop` する。却下・修正になったときに戻す手間が出るうえ、クラウドセッションでは止まるたびに環境側の Stop hook が未コミットの変更の commit / push を求めるため
6. **承認した設計を Issue に残す**: 承認を得たら、設計の要点（変える範囲・方針・検証方法）を `add_issue_comment` で Issue にコメントする（見出しは `## 設計（承認済み）`）。セッションが長くなって compaction が入っても、細部をここから読み直せるようにするため。Phase 5 で設計を更新したら、このコメントを `update_issue_comment` で直す（2 件目を書き足さない）。コメントの `id` は投稿したときの応答から控え、手元に無ければ（compaction の後など）`issue_read`（method: `get_comments`）で本文が `## 設計（承認済み）` で始まるコメントを探して取る。Phase 4 を省いたときと、無人実行（`.claude/routines/weekday-issue-start.md`。設計は PR 本文に書く）では書かない

```
## 設計案の比較

### 案1: 最小変更
- 変更ファイル: 2個
- メリット: 低リスク、早い
- デメリット: 既存コードとの結合度が高い

### 案2: クリーン設計
- 変更ファイル: 5個（新規2個）
- メリット: テストしやすい、拡張性が高い
- デメリット: 工数が多い

### 案3: 実用的バランス（推奨）
- 変更ファイル: 3個（新規1個）
- メリット: 適度な分離、現実的な工数
- デメリット: 一部結合が残る

→ 案3を推奨します。理由: ...
変える範囲: <ファイル・領域>（目的のために作り直す周辺: なし / <箇所と理由>）
検証方法: <どのテスト・動作確認で DoD を確かめるか>
近似・既知の制限（推奨案）: なし / <置くなら、最悪の入力（間隔を大きく空ける・空や最大の入力など）で何が起きるかを 1 行で。仕様で決まる境界条件そのものは、手順 4 の仕様の質問に回す>

```

## 必須チェック項目（系統スキルの網羅性）

FF14 のスキル系統（例: ファイア系 = ファイア / ファイラ / ファイガ / ファイジャ / ハイファイラ など、ブリザド系 = ブリザド / ブリザラ / ブリザガ / ブリザジャ / ハイブリザラ など、グレア系 = グレア / グレアガ / グレアジャ）に対し、新仕様（バフ効果／MP消費／威力倍率／リソース連動 等）を適用する設計では、系統内の全スキルが新仕様の対象になっているかを設計時に確認する（Issue #231 で導入）。スキル以外でも「同じ扱いをすべき類似要素のグループ」（同系統のデータ定義群・同じインターフェースを実装するクラス群・同種のイベントハンドラ群）なら同じ手順を適用する。

1. 対象系統の全スキル ID を `Grep` で列挙する（例: `Grep -n "id:.*blizzard" src/client/data/`）
2. 各スキルが新仕様の経路を通るかを `code-architect` の設計案レベルで確認する
3. 一部しか対象にならない設計案なら、系統横断テストの要否をここでユーザーと合意しておく（Phase 5 に伝播）

過去事例: Issue #210 で「通常ブリザド」のみ確認して設計を進め、ブリザジャでバフが反応しない手戻りが発生（#195 知見ボードコメント参照）。

> 代表 1 要素だけ確認して進めると、残りの要素で新仕様が効かない手戻りが起きやすい。「1 つ動いた＝全部動く」とは限らない。

## 置き場所を変える設計のチェック

規約・手順・ドキュメントの置き場所を変える設計（rules から skill への移動、ファイルの分割・統合など）では、移動先ごとに層と読み込まれる契機を設計案に書く。層は `.claude/rules/documentation-policy.md`「読み込みタイミングで 3 層に分ける」の 3 つで、契機は次のどれか。

- 常駐: 毎セッションの起動時
- オンデマンド: skill の呼び出し（と、そこからのパス参照）／`paths:` に一致するファイルの Read・Edit・Write／サブエージェントの起動時（`.claude/agents/*.md`）
- 人間向け: Claude は読まない

どの層にも当たらない移動先（rules・skills・agents・`docs/`・README のどれでもない、独自ディレクトリのファイルなど）を選んだ案や、Claude が判断に使う情報を人間向けの層に移す案は、提示する前に直す。Claude がその場面で辿り着く経路が、常駐ファイルからの 1 行の案内しか残らないため。
