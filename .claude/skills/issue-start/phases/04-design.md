# Phase 4: 設計（code-architect）とユーザー承認

**目的**: 実装に入る前にアプローチをユーザーと合意する。設計の合意が手戻りを防ぐ。**設計承認はこのワークフローで最も重要な確認ポイント**で、承認された設計が Phase 5 のスコープになる。

## いつ設計 Phase を行うか

| 状況 | 動き |
|------|------|
| 差分を 1 文で説明できる（1〜2 ファイルの明確な修正、Issue に実装方針が書いてある） | Phase 4 をスキップし、方針を 1〜2 行で述べて Phase 5 へ |
| 複数ファイルに跨る／馴染みのない領域／アプローチに迷いがある | `code-architect` を **1 個** 起動し、推奨案をユーザーに提示して承認を得る |
| 設計の方向性自体に選択肢がある（最小変更か、構造を直すか） | 観点を変えて **2〜3 個** 並列に起動し、比較して推奨案を示す |

Claude Code の **plan mode** で作業しているときは、設計案の提示と承認を `ExitPlanMode` の承認フローに乗せてよい（承認後に Phase 5 の編集が解禁される）。

## 実行手順

1. Phase 3 の探索結果を踏まえ、`Agent` ツールで `subagent_type: "code-architect"` を起動する（定義は `.claude/agents/code-architect.md`）。1 個のときは「既存パターンに沿った実用的な設計」を依頼する
2. 複数起動するときは観点を分ける：
   - **最小変更**: 「既存コードへの変更を最小限にし、最大限再利用するアプローチで設計して」
   - **クリーン設計**: 「保守性・テスタビリティを重視した構造で設計して」
   - **実用的バランス**: 「実装速度とコード品質のバランスを取るアプローチで設計して」
3. 各プロンプトに Issue の要件・DoD・Phase 3 で分かった重要ファイル・返却量の上限を含める
4. 結果を比較し、**推奨案を理由付きでユーザーに提示** する。Issue の DoD を満たす最小の変更を基準にし、頼まれていない抽象化や拡張点は入れない
5. **ユーザーの承認を得てから** Phase 5 に進む

## 提示フォーマット

```
## 設計案の比較

### 案1: 最小変更
- 変更ファイル: 2個
- メリット: 低リスク、早い
- デメリット: 既存コードとの結合度が高い

### 案2: クリーン設計
- 変更ファイル: 5個（新規2個）
- メリット: テストしやすい、拡張性が高い
- デメリット: 工数が多い

### 案3: 実用的バランス（推奨）
- 変更ファイル: 3個（新規1個）
- メリット: 適度な分離、現実的な工数
- デメリット: 一部結合が残る

→ 案3を推奨します。理由: ...
検証方法: <どのテスト・動作確認で DoD を確かめるか>

どの案で進めますか？（案番号、または修正点を指定してください）
```

## 必須チェック項目（系統スキルの網羅性）

FF14 のスキル系統（例: ファイア系 = ファイア / ファイガ / ファイジャ、ブリザド系 = ブリザド / ブリザガ / ブリザジャ、グレア系 = グレア / グレラ / グレアガ / グレアジャ）に対し、新仕様（バフ効果／MP消費／威力倍率／リソース連動 等）を適用する設計では、**系統内の全スキルが新仕様の対象になっているか** を設計時に確認する（Issue #231 で導入）。スキル以外でも「同じ扱いをすべき類似要素のグループ」（同系統のデータ定義群・同じインターフェースを実装するクラス群・同種のイベントハンドラ群）なら同じ手順を適用する。

1. 対象系統の全スキル ID を `Grep` で列挙する（例: `Grep -n "id:.*blizzard" src/client/data/`）
2. 各スキルが新仕様の経路を通るかを `code-architect` の設計案レベルで確認する
3. 一部しか対象にならない設計案なら、系統横断テストの要否をここでユーザーと合意しておく（Phase 5 に伝播）

過去事例: Issue #210 で「通常ブリザド」のみ確認して設計を進め、ブリザジャでバフが反応しない手戻りが発生（#195 知見ボードコメント参照）。

> 代表 1 要素だけ確認して進めると、残りの要素で新仕様が効かない手戻りが起きやすい。「1 つ動いた＝全部動く」とは限らない。
