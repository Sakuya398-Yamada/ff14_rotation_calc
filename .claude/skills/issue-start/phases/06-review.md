# Phase 6: コードレビュー（code-reviewer）

**目的**: PR を作る前に、実装した本人とは **別のコンテキスト** でコードを批判的に読み、バグ・規約違反・DoD の取りこぼしを見つける。自分が書いたコードを自分で見直すだけでは、書いたときの前提に引きずられて見落とす。

## 実行手順

1. **決定論的なゲートを先に通す**: テストスイート全体・リント・型チェックを実行し、通っていることを確認する。落ちていれば Phase 5 に戻る。レビュアーに「リンターが見つけること」を探させない
2. **レビュアーの起動数を決める**:

   | 差分の規模 | 起動 |
   |-----------|------|
   | 小（1〜2 ファイル、数十行） | `code-reviewer` 1 個（観点: バグと DoD 充足） |
   | 中〜大、複数領域 | 2〜3 個を並列。観点を分ける |

3. `Agent` ツールで `subagent_type: "code-reviewer"` を起動する（定義は `.claude/agents/code-reviewer.md`）。起動する前に、主セッションで `git fetch origin main` を 1 回だけ実行する。プロンプトに **Issue 番号・DoD・レビュー範囲（既定は `origin/main...HEAD` と未コミット分。Phase 2・7 と同じ基準で、ローカルの `main` には依存しない）・観点** と、「`origin/main` は fetch 済みなので fetch しない」を書く。並列に起動したレビュアーがそれぞれ fetch すると、同じ ref の更新がぶつかり、片方が ref ロックの競合で失敗する。観点の例：
   - **バグ・機能的正確性**: ロジックエラー、境界条件、エラー処理、並行性
   - **要件充足**: Issue の DoD と設計との対応、同系統要素の網羅性
   - **ランブック（手順・コマンドを含むドキュメント）**: コマンドの構文と実行可能性、他ファイルから参照される節番号・見出しの整合（振り直しで参照がずれていないか）、手順どおりに動くか（構造的に到達しない分岐が無いか）
   - **移動・分割・重複解消**（記述を別ファイルへ移す・まとめる変更）: 削除した行が持っていた規約・判断基準・コマンド・事実が、変更後もどこかに残っているか（消すなら意図して消したか）を、削除した行ごとに照合する。実装した本人は「移動先に手順があるか」だけを見て、移動元にしか無かった補足を見落としやすい
   - **規約・アーキテクチャ**: `CLAUDE.md` と `.claude/rules/*.md` の遵守、既存構造との整合、重複
   - **作業ブランチの検証（必須）**: サブエージェント完了直後、指摘の集約に入る前に `git branch --show-current` を実行し、当該 Issue の作業ブランチ（`<type>/<issue番号>-<desc>`）が維持されているか確認する。一致しない場合は **以降の作業を止めて** `git switch <作業ブランチ>` で復帰してから続行する（未コミット変更があれば取り扱いをユーザーに確認）。背景: サブエージェントが差分確認の過程で checkout を実行し、メインリポが `main` に切り替わっていた事故への二重ガード（Issue #294、発生元 #269）。エージェント定義側の読み取り専用制約（`.claude/agents/*.md`）と併用する
4. 各レビュアーの指摘（信頼度 80 以上）を集約し、重複を除いて重要度順に並べる。`[scope-out]` の指摘はスコープ外候補に分ける
5. **UI 動作確認（フロントエンド変更を含む場合のみ）**: Playwright MCP で `browser_navigate` → `browser_snapshot` により動作を確認する（手順・DnD 検証・React 制御フォームのワークアラウンドは `.claude/skills/playwright-mcp/SKILL.md`）。MCP 未接続なら、クラウドセッションでは `playwright-mcp/SKILL.md`「MCP が使えないとき」の方法で確かめる。開発サーバーが起動できない、ローカルで MCP 未接続、またはクラウドでこの方法もできないなら、ユーザーに手動確認を依頼し **未検証である旨を完了報告に明記する**
6. **スコープ内／外の仕分け**: 指摘を当該 Issue の DoD に照らして分ける
   - **スコープ内**: このブランチで修正する（Phase 5 に戻る）
   - **スコープ外**: 起票候補として別管理する（当該 PR に混ぜない）
   - 起票判定基準は `SKILL.md`「スコープ外問題の起票提案」
7. **ユーザーに聞くものを絞る**（`SKILL.md`「全体ルール」の確認ポイントに揃える）:
   - スコープ内の指摘: 聞かずに直し、何を直したかを進捗として共有する。直すと承認された設計から外れるものは、Phase 5「実装」手順 1 と同じく理由を添えて報告してから直す（次の聞くものにも当たるなら、報告で済ませず聞く）。直すと DoD やスコープが変わるもの、手順書・規約から人の確認を外す・弱めるもの（`phases/04-design.md`「いつ設計 Phase を行うか」の 1 行目）、無人ルーティン（`.claude/routines/`）の書き込み・判断の手順（ルーティンが判定基準として参照する skill の手順と、ルーティンが書き込み（起票・コメント投稿・コメント編集など）に使うコマンド例（`pitfalls-cloud.md` のフォールバック。テンプレート更新で変わる場合も同じ）を含む。取得だけのコマンド例・PR 作成の例と、`weekday-issue-start` が従う `/issue-start` の手順は除く）を変えるもの（同じ表の 2 行目）、直すかどうかで判断が分かれるもの（指摘が正しいか疑わしい、直すコストが見合わない等）だけ、今すぐ修正 / 後で対応 / このまま進める をユーザーに聞く。ルーティンの手順を変えるものは、当てる文面を示し、今すぐ修正にその修正をコミットして push する承認も含めて、1 つの質問で取る
   - スコープ外の指摘: `SKILL.md`「起票フロー（共通）」手順 1・2 で重複を確かめてから提示し、Y（そのまま起票）/ E（編集して起票）/ A（既存 Issue に追記。重複候補があるときだけ）/ U（起票せず還元に回す。還元先がテンプレート汎用のときだけ）/ N（起票しない）を聞く（確認ポイントの「スコープ外問題の起票」）
8. スコープ内の修正を適用し（聞いたものは指示に従う）、テストを再実行する
9. スコープ外の指摘は、Y / E なら `SKILL.md`「起票フロー（共通）」手順 3 のとおり sub-issue として起票し（本文の構成・`依存:` の書き方もそこにある）、A なら起票せず既存 Issue にコメントで追記する。U なら起票せず、Phase 8 手順 5 の知見ボードの候補として控える（同「書き込み手順」1 で棚卸しする）

> Claude Code 組み込みの `/code-review`（新しいサブエージェントで差分のバグを探す）や `/security-review` で代用・補強してもよい。その場合も手順 6 以降の仕分けは同じ。

## スキップ条件

- 散文のみのドキュメント変更（説明・規約・README 等）。`docs` ラベルでも、**実行手順・コマンド・他ファイルから参照される節番号を含むランブック**（スケジュールタスクのプロンプト、hooks の手順、skills の phases、取り込み手順等）と、**記述を別ファイルへ移す・まとめる変更**（観点は手順 3「移動・分割・重複解消」）はスキップせず `code-reviewer` を 1 個起動する。散文と違い、コマンドの構文・他ファイルからの参照・手順の実行可能性にバグが入るため（観点は手順 3）
- ユーザーが明示的にスキップを指示した場合

## ワークフロー改善余地のメモ（Phase 8 向け）

レビュー手順やサブエージェント運用への気づき（観点の過不足・並列数の妥当性・信頼度しきい値の感触など）があれば短文メモで控え、Phase 8 で知見ボード（#195）にユーザー確認のうえ書く（`phases/08-issue-recording.md`）。
