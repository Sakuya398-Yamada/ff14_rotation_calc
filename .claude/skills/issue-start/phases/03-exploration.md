# Phase 3: コード探索（code-explorer）

**目的**: 実装に入る前に、既存コードの構造・パターン・関連箇所を理解する。ここでの理解が設計と実装の質を決める。主会話のコンテキストに生の探索ログを入れず、要約だけを受け取るためにサブエージェントを使う。

## 起動数の決め方

| Issue の規模 | 探索の仕方 |
|-------------|-----------|
| 1〜2 ファイルで閉じる修正、既知の箇所 | 自分で Grep → 局所読み。サブエージェントは起動しない（Phase 3 をスキップしてよい） |
| 1 領域の実装（数ファイル） | `code-explorer` を 1 個 |
| 複数領域を跨ぐ、類似機能・影響範囲・アーキテクチャを別々に知りたい | `code-explorer` を 2〜3 個並列。観点を分け、重複させない |

## 実行手順

1. Issue の要件と、Phase 1 で引き継いだ未確定事項の調査（「`/issue-start` の探索で調べる」の項目）に基づき、`Agent` ツールで `subagent_type: "code-explorer"` を起動する（定義は `.claude/agents/code-explorer.md`。システムプロンプトの再供給は不要）
2. 複数起動するときは観点を分ける：
   - **類似機能の調査**: 「Issue 要件に類似する既存機能の実装をトレースして」
   - **アーキテクチャ把握**: 「変更対象領域の構造・抽象化・データフローをまとめて」
   - **影響範囲の特定**: 「この変更が影響するコンポーネント・テスト・依存関係と、変更前の仕様を前提にした利用者向けドキュメント（README の制限事項など）の記述を特定して」
3. 各プロンプトに **目的・スコープ・返却フォーマットと上限・除外** を書く（`.claude/rules/context-efficiency.md`「委譲時のプロンプトに含めるもの」）。「重要なファイル 5〜10 個のリストを含めて」と依頼する
4. 結果を受け取ったら、リストアップされたファイルのうち実装に直結する箇所を **自分で局所的に読んで** 理解を裏取りする。大きなファイルは Grep で該当行を特定してから `offset` / `limit` で読む。探索中は作業ツリーを変えない（設計承認まで変えない理由は `phases/04-design.md` 手順 5）
5. **ライブラリ仕様の確認（必要な場合のみ）**: 使用するライブラリ（React, Hono, Prisma 等）に不明点があれば context7 等のドキュメント参照 MCP（本リポジトリでは未登録）か公式ドキュメント（`WebFetch`）で確認する
6. 探索結果を **「把握したこと／未確定のこと／次の計画」** の 3 点で 3〜6 行にまとめてユーザーに共有する。読み方が分かれて成果物が変わる点があれば、この時点で質問する。単なる進捗共有なら回答を待たずに Phase 4 へ進む
7. **スコープ外問題の一覧化**: 探索中に当該 Issue のスコープ外の問題（別バグ／設計上の違和感／データ誤り等）を見つけた場合、一覧化と重複確認は Phase 末尾で済ませる。候補の提示と確認は、Phase 4 を行うなら設計案と一緒に出し、同じ呼び出しで別々の質問にして聞く（`SKILL.md`「全体ルール」の「確認の聞き方」。plan mode なら、そこにあるとおり設計承認より先に聞く）。Phase 4 を省くなら、Phase 3 の末尾で聞いてから Phase 5 に進む
   - 起票判定基準（`SKILL.md`「スコープ外問題の起票提案」）で候補を絞る
   - 重複確認・提示・起票は `SKILL.md`「起票フロー（共通）」の手順どおりに行う（本文の構成と、親の未マージの変更を前提にするときの `依存:` もそこにある）
   - 見つからなかった場合は「スコープ外問題の検出: なし」と一言添える

## 並列起動の例

```
Agent(subagent_type: "code-explorer", prompt: "目的: Issue #42 のバフ適用順序の修正に先立ち、ダメージ計算ロジックの構造を把握する。スコープ: src/client/logic/ 配下（resolve-timeline.ts ほか）と、それを呼ぶコンポーネント。返却: エントリポイント・データフロー・依存関係を各箇所 file:line + 3〜5 行の要約で、関連ファイル 5〜10 個のリスト付き。合計 400 行以内、コード引用は 1 箇所 10 行以内。除外: import 文と型定義の列挙。")
Agent(subagent_type: "code-explorer", prompt: "目的: 同 Issue の UI 側の変更点を見積もる。スコープ: src/client/components/ のスキル選択 UI・タイムラインと状態管理。返却: 状態管理・データ変換の要点を各箇所 file:line + 3〜5 行で、関連ファイル 5〜10 個のリスト付き。合計 400 行以内。除外: スタイル定義の列挙。")
```

> Claude Code 組み込みの `Explore` エージェントでも代用できるが、`code-explorer` は `CLAUDE.md` / `.claude/rules/` とプロジェクト固有の文脈（定義ファイル末尾の Project Context）を読んだ上で動き、返却量の既定値を持つ点が異なる。

## スキップ条件

以下の場合は Phase 3 を飛ばして Phase 4 または 5 に進んでよい：

- Issue ラベルが `bug` で、修正箇所が明確な 1 ファイル程度の変更
- Issue ラベルが `docs` のドキュメント変更
- ユーザーが明示的にスキップを指示した場合

スキップしても、利用者から見える挙動・上限・制約を変える Issue（ラベルを問わない。`bug` の修正でも上限や挙動が変わるなら当たる）では、利用者向けドキュメント（README の制限事項・既知の制約・FAQ など）を変える仕様のキーワードで Grep し、食い違う記述が無いかだけは見る。この Issue の変更で誤りになる記述は、不可避な副次変更として同じ PR で直し、PR 本文の「## 変更点」に書く。書き換えの目的が別になるものは、スコープ外として起票を提案する
