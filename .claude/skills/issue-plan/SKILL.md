# Issue計画スキル（/issue-plan）

入力: $ARGUMENTS

ユーザーの要望を、`/issue-start` で 1 回に回せる粒度の GitHub Issue に落とし込み、ユーザー確認を挟んで起票する。

## 使い方

```
/issue-plan ユーザー設定画面を追加したい
/issue-plan #12
/issue-plan
```

- 入力が要望の文章なら、それを起点に分割案を作る
- 入力が Issue 番号なら、その Issue が大きすぎる前提で既存 Issue の分割を行う
- 入力が無ければ、手順 1 の質問から始める

## 判断基準

- **粒度・依存関係・親Issue**: 後述「粒度の判定」（正本）
- **本文の構成**: `.claude/rules/git-conventions.md`「Issue のタイトルと本文」の見出し構成（背景・目的 / 要件（やること・やらないこと）/ 完了条件（DoD）/ 未確定事項）
- **タイトル・ラベル**: `<ラベル名>: <簡潔な説明>`、ラベルは `feature` / `bug` / `refactor` / `docs` のいずれか
- **GitHub 操作**: `.mcp.json` の GitHub MCP（`github-mcp-server` バイナリ、`.claude/rules/mcp-setup.md`）。未接続・エラー時（使うツールがツール一覧に無いときも含む）は `gh` CLI（`/c/Program Files/GitHub CLI/gh.exe`。クラウドセッションでは手順 5 の `gh issue create` / `gh issue edit` が GraphQL で 403 になるので、`.claude/skills/issue-start/pitfalls-cloud.md`「クラウドセッションでは gh の GraphQL 系が使えない」の REST に置き換える）、それも無ければ整形済み本文を提示して起票を依頼する

## 粒度の判定

既定は `.claude/rules/git-conventions.md`「粒度」。分けるかどうかは以下で判定する。

| 分ける（複数 Issue にする） | 分けない（1 Issue に保つ） |
|---------------------------|--------------------------|
| 「やること」に目的の異なる項目が並ぶ（「○○を追加し、ついでに目的と関係ない△△を直す」） | 片方だけ入れると動作しない・検証できない（型定義とその唯一の利用箇所など） |
| 片方の結果を見ないともう片方の設計が決まらない（依存順に分け、後続に `依存: #N`。両方を 1 つの設計案で決められるなら当たらない） | 目的のために明らかに要る周辺の作り直し（足す変更が既存の重複やつぎはぎを増やすときの、その箇所の重複の統合・リファクタなど）。ラベルは目的の側（`feature` など）にする |
| 設計案が 1 回の承認で判断しきれない（互いに独立した設計判断が複数並び、別々に承認・却下したくなる） | 層をまたいでも、1 画面・1 機能として縦に切った方が検証しやすい |
| 一部だけ先にマージしたい・一部だけ戻したくなる塊がある | 分けた片方が、それだけでは完了条件を確かめられない |
| | 1 つのパターン（規約・書き方）を多数のファイル・データに機械的に当てる（文言の辞書化・データ形式の移行など）。パターンを決める部分だけを先の Issue に分け、その完了条件に、決めたパターンを後のセッションが読む場所（`coding-standards.md` など）に書くことを入れる。当てる部分は、パターンごとに 1 Issue に保つ。範囲で細切れにすると、Issue ごとのセッションで判断が揺れて整合が崩れる。一部の範囲だけ先にマージしたいとき（最初の範囲の PR を手本として確かめてから残りに当てたい、など）は、同じパターンのまま範囲で分け、後の Issue に先の Issue への `依存:` を書いて、先の PR を手本にする |

迷ったら「このIssueのPRだけをマージしても、壊れず・単独で説明できるか」で判定する。Yes なら粒度は適切。表の両側に当てはまるときは、分けたときの各候補にこの問いを当てる（「単独で説明できる」は、その PR だけで完了条件を確かめられること）。すべて Yes なら分ける。No の候補が出たら、その候補を使う側の候補に含めた分け方で問い直し、それでも No が残るなら分けない。ただし、目的のために明らかに要る周辺の作り直し（右列 2 行目）と、1 つのパターンを機械的に当てる作業（右列の最後の行）は、この問いで分けない（作り直しだけの候補も、範囲で細切れにした候補も、それぞれ Yes になってしまうため）。

- 先に別 Issue の完了が必要な場合の書き方は `.claude/rules/git-conventions.md`「粒度」（起票時の付け方は手順 5）
- 1 つの要望を 3 件以上に分割したときは、進捗管理用の親Issue を作ってよい。親Issue 自体は実装対象ではないので `/issue-start` しない
- 親子関係は GitHub の sub-issue で紐づける（GitHub MCP: `issue_write` の `parent_issue_number`、既存 Issue なら `sub_issue_write`）。親Issue には進捗が自動集計される。sub-issue を作れない環境での代用は手順 5 の 5

## 手順

### 1. 要望の把握（不足があれば質問して止まる）

以下が揃っているかを確認し、足りなければ推測せずに質問する。質問は 1 回にまとめ、可能なら選択肢を添える（`AskUserQuestion` が使えるなら選択式で）。手順 2 の調べで質問が増えそうなら、手順 2 を先に済ませてから、まとめて聞く。

| 項目 | 確認内容 |
|------|---------|
| 背景・目的 | なぜ必要か。誰が困っているか |
| やりたいこと | 期待する振る舞い・成果物 |
| やらないこと | 今回のスコープから外すもの |
| 制約 | 期限・互換性・対象環境・使ってよい技術 |
| 完了の判断基準 | 何が確認できれば完了か |

表の項目の不足とは別に、要望に無い仕様の分岐に気付いたとき（手順 2 の調べで気付いた場合も）は、起票前に答えが要るもの（答えで Issue の数・境界・依存、または完了条件の確かめ方が変わるもの）だけを質問に入れる。完了条件の値や文言が変わるだけのものは質問で止まらず、手順 3 の未確定事項（`[要確認]`）に回し、`/issue-start` で着手するときに確かめる。ユーザーが「まだ決めていない」と答えた分岐は、もう一度は聞かない。「やらないこと」に入れて決まってから起票するか、判断材料を集める調査だけの Issue を先に起票するかを選んでもらう。

入力が既存 Issue 番号の場合は、`issue_read`（method: `get` / `get_comments`）で本文・コメントを取得し、それを要望として扱う。

### 2. 現状の把握（軽量に）

1. **重複・関連 Issue の検索**: `search_issues`（`owner` / `repo` を指定、query は自然文）で検索する。`search_issues` がツール一覧に無いか拒まれたら、`.claude/skills/issue-start/pitfalls-cloud.md`「クラウドセッションでは gh の GraphQL 系が使えない」の重複検索で代える。重複候補があればリンクを提示し、新規起票ではなく既存 Issue へのコメント追記・本文更新を提案する。ただし、バグ報告で当たったのが完了済み（`state_reason` が `completed`）の Issue なら、重複ではなく下の 6 の由来の Issue の候補として扱い、それに紐づけた新規起票を提案する（完了済みの Issue は PR がマージ済みで、追記しても着手されない）
2. **技術前提の実在確認**: 要望に「○○を新規実装する」のような技術前提があれば `Grep` で実在を確認する。既に存在すればスコープを縮める
3. **既存構造の把握（必要な場合のみ）**: 大きめの機能で、既存構造を知らないと分割できない場合に限り、`code-explorer` を 1 個起動する。返却量の上限（例: 「`file:line` と 3 行以内の要約のみ、合計 200 行以内」）を明記する（`.claude/rules/context-efficiency.md`）。全読みはしない
4. **依頼された調査**: 要望の中で「〜を調べてほしい」と頼まれた調査は、この手順と同じ軽さ（Grep・局所読み・公式ドキュメントやパッケージ情報の参照・既存のコマンドで現状値を読む程度。コードを跨ぐなら `code-explorer` を 1 個まで起動してよく、3 と兼ねる）で済むなら、ここで済ませて結果を本文の「補足」に書き、手順 4 の提示にも載せる。それを超えるもの（試作・新しい依存を入れての計測・`code-explorer` 1 個に収まらない調査）は、未確定事項に「`/issue-start` の探索で調べる」と書いて回す（`[要確認]` はユーザーに聞く項目の印なので付けない）。調査の結果次第で分割の仕方が変わるなら、調査だけの Issue を先に起票し、残りの分割はその結論を受けて改めて `/issue-plan` で行う
5. **利用者向けドキュメントの記述（利用者から見える挙動・上限・制約を変える要望のみ。ラベルは問わない）**: README の制限事項・既知の制約・FAQ などを、変える仕様のキーワードで Grep する。変更後と食い違う記述があれば、その書き換えを候補の「やること」に含める（目的が別なら別の候補にする）。`/issue-start` は修正箇所が明確な bug で Phase 3 を飛ばせるので、ここで拾っておく
6. **バグの由来の Issue（bug の候補になる要望のみ）**: 完了済みの Issue の成果物に入った不具合なら、その不具合を入れた Issue（由来の Issue）を次の順に探し、下の段落の条件に合うものが見つかったところで止める
   1. 報告に Issue・PR の番号があれば、それ
   2. 不具合の箇所（ファイル・関数）が分かるなら（報告に無ければ、機能名や画面の文言を `Grep` して実装のファイルに当たりを付ける。当たらなければこの 2 は飛ばす）、`git log --format='%h %s' -n 20 -- <パス>`（識別子で探すなら `git log -S '<識別子>' --format='%h %s'`）で、その箇所を入れた・変えたコミットを見る。件名の末尾は Issue 番号で、squash マージの件名には `(#<PR番号>)` も付く（`.claude/rules/git-conventions.md`「コミットメッセージ」）。件名に番号が無いコミットは、`gh api "repos/{owner}/{repo}/commits/<ハッシュ>/pulls" --jq '.[].number'` でそれを含む PR を引く
   3. 手順 2 の 1 の検索で当たった完了済みの Issue

   拾った番号は `issue_read`（method: `get`）で読む。PR なら、本文の `closes` / `fixes` / `resolves` / `refs #N` の Issue を読む。閉じた理由が `completed` で、不具合の箇所に関わる完了条件を持つものを由来の Issue とする。Issue に行き着かないマージ済みの PR は、その PR を由来の Issue の代わりにする。候補が複数残る・確信が持てないときは 1 件に絞らず、根拠を添えて手順 4 で選んでもらう。見つからなければ紐づけずに起票する

### 3. 分割案の作成

1. 「粒度の判定」表に従って Issue 候補に分割する
2. **依存順に並べる**（基盤 → 利用側）。並列に進められる候補はそう明記する。基盤だけでは完了条件を確かめられないなら、独立した候補にせず、最初の利用側の候補に含める
3. 各候補に以下を揃える：
   - タイトル（`<ラベル名>: <簡潔な説明>`）とラベル
   - 背景・目的（1〜2 文）
   - やること／やらないこと
   - 完了条件（検証可能なチェックリスト。「やること」の言い換えではなく、動作確認・テストの観点で書く）。数値目標（行数・件数・時間など）を置くときは、現状値を測って本文に添え、スコープ内で届くかを確かめる
   - 依存（`依存: #N`。まだ番号が無い候補への依存は「候補 2 に依存」と書く）
   - 由来（手順 2 の 6 で由来の Issue を紐づけた候補のみ）: 「## 関連Issue」に `由来: #N` と書き、完了条件に `#N の完了条件のうち <今回の修正が触れる項目> が引き続き満たされる` を足す。項目は #N の完了条件から、直すファイル・振る舞いに関わるものを 1〜3 個書き写す（絞れなければ「#N の完了条件が引き続き満たされる」とだけ書く。由来が PR なら、完了条件の代わりに `#<PR> で入れた <振る舞い> が引き続き動く` と書く）。直すと #N の完了条件そのものが変わる（その条件が不具合の元になっている）なら、その項目は書き写さず、変えることを「やること」に書いて、変え方を未確定事項（`[要確認]`）に回す
   - 未確定事項（あれば。要確認の仕様は `[要確認]` を付けて本文に残す）。`[要確認]` の答えで変わる完了条件は、答えを先取りして書かない（「〜のとき既定値になる」ではなく「〜のときの扱いが、未確定事項で決めたとおりになる」）。先取りした行は、`/issue-start` で別の答えに決まったときに食い違ったまま残る。日次の無人実装（`weekday-issue-start`）は `## 未確定事項` に `[要確認]` の項目がある Issue を選ばない。`## 要件` など別の節に「ここで決める」と書くと選定をすり抜けるので、決定待ちは `## 未確定事項` に置く
   - 手がかり（分かる範囲で関連ファイルや既存の類似実装。本文の「## 補足」に書く）
4. 候補が 3 件以上になったら、進捗管理用の親Issue を作るかを選べるようにする（「粒度の判定」）

### 4. ユーザー確認（必須）

以下のフォーマットで提示し、承認を得るまで起票しない。中身（【Issue計画】から推奨着手順まで）はメッセージ本文に出し、末尾の「起票しますか？」は `AskUserQuestion` の選択式の質問で聞く（選択肢は [Y] と [N]。[E] は自由記述（Other）で修正内容を受ける。候補ごとには分けず 1 問で聞く。使えないときは末尾もテキストで出す）。

```
【Issue計画】要望: <1行要約>
重複・関連Issue: なし / 既存 #NN（→ 統合 or 参照）
由来の Issue（bug のみ）: なし / #NN <タイトル>（根拠: コミット <ハッシュ> の件名 / 報告の番号 / 検索） / 候補 #NN（根拠: …）・#MM（根拠: …）（どれかを選ぶ）
調査結果: なし / <依頼された調査の結果を 2〜3 行>（→ 候補N の補足）
還元先: なし / 候補N はテンプレート汎用（→ 起票せず還元を提案）

候補1  <ラベル>: <タイトル>
  目的: <1〜2文>
  やること: <箇条書き> ／ やらないこと: <箇条書き>
  DoD: - [ ] ... - [ ] ...
  依存: なし
  由来: #NN（由来の Issue を紐づけた候補のみ）

候補2  <ラベル>: <タイトル>
  ...
  依存: 候補1

親Issue: 作る（<タイトル>） / 作らない
推奨着手順: 候補1 → 候補2（候補3 は並列可）

起票しますか？
 [Y] この内容で全件起票（「還元先」の行に挙げた候補は除く）
 [E] 編集する（候補番号と修正内容を指定。「候補1と2をまとめて」のような粒度の修正も可）
 [N] 起票しない（計画の提示のみ）
```

- [E] の場合は修正を反映して再提示し、改めて Y/E/N を取る
- 由来の Issue の候補が複数のときは、[E] でどれかを選んでもらう。選ばずに [Y] なら、由来を書かずに起票する
- 一部の候補だけ起票したい場合は、Other（テキストで聞いたならその返答）で候補番号を指定してもらう
- ワークフロー自体（`CLAUDE.md`・`.claude/`・`.github/ISSUE_TEMPLATE/`）の改善の候補は、`.claude/rules/workflow-feedback.md`「還元する / しないの判定」で還元先を決め、テンプレート汎用なら「還元先」の行に挙げて [Y] の起票から外す（同じファイル「テンプレート元への還元」）。外した候補は、計画への [Y] とは別に、`/issue-start` の `phases/08-issue-recording.md` 手順 5 の提示と確認を経て知見ボードに `還元先: テンプレート汎用` で書き、手順 6 の確認を経て還元する。いまの作業を塞いでいる不具合で、このプロジェクトでも先に直すとユーザーが決めたとき（[E] でその候補を起票に戻す）だけ起票する（`.claude/skills/issue-start/SKILL.md`「起票フロー（共通）」と同じ）

### 5. 起票

1. **親Issue を作る場合は先に作る**（`issue_write`、method: `create`）。ラベルは子 Issue の多数派（例: `feature`）。本文に目的と「このIssueは進捗管理用。`/issue-start` の対象にしない」を明記する
2. 子 Issue を依存順に 1 件ずつ起票する（`issue_write`、method: `create`）。親がある場合は `parent_issue_number` に親の番号を渡して sub-issue として作る。本文は `git-conventions.md`「Issue のタイトルと本文」の構成に揃える。由来の Issue を紐づけた候補は「## 関連Issue」に `- 由来: #N` を書く（#N は閉じているので、依存関係（blocked by）は付けない）
3. 後続 Issue の `依存: #N` は、先行 Issue の実番号に置き換えてから起票する。起票したら、`.claude/skills/issue-start/dependencies.md`「付け方」で GitHub の依存関係（blocked by）にも付ける（`gh` が無いときの画面から付ける案内は、手順 6 の結果の提示で行う）
4. ラベルを付ける（権限が無ければ省略してよい。`/issue-start` Phase 2 で判定される）
5. sub-issue を作れない環境（`gh issue create` が `--parent` を持たない版など。`gh api` の REST なら `issues/<親番号>/sub_issues` で紐づけられるので代用は要らない）では、親本文のタスクリスト `- [ ] #N <タイトル>` と各子 Issue 末尾の `親Issue: #<親番号>` で代用する（`issue_write` method: `update` / `gh issue edit`）。クラウドセッションでは `gh issue edit` が GraphQL を使うので 403 になる。本文は REST の `gh api -X PATCH repos/{owner}/{repo}/issues/N -F body=@<file>` で更新する（`.claude/skills/issue-start/pitfalls-cloud.md`「クラウドセッションでは gh の GraphQL 系が使えない」）。`/issue-start` がスコープ外問題で起票する子Issue も同じ扱い
6. **起票に失敗した場合**（権限・ネットワーク等）: 整形済み本文を提示して手動起票を案内する。`gh issue create --title ... --label ... --body-file <tmp>` へのフォールバックも可。クラウドセッションでは `gh issue create` も 403 になるので、REST の `gh api repos/{owner}/{repo}/issues -f title=... -F body=@<tmp> -f "labels[]=..."` で起票する。親がある場合は、続けて手順 5 と同じ pitfalls-cloud.md の節にある `sub_issues` の REST で sub-issue に紐づける

### 6. 結果の提示

- 起票した Issue の一覧（番号・タイトル・依存）と推奨着手順を提示する
- 次のアクションとして `/issue-start #<最初に着手するIssue>` を案内する
- このセッションでワークフロー自体への気づき（粒度規約の曖昧さ、質問項目の不足等）があれば、`.claude/skills/issue-start/phases/08-issue-recording.md` 節 5「ワークフロー改善余地の知見ボードへの記録」の提示と確認を経て、知見ボードに追記する（還元先の判定は `.claude/rules/workflow-feedback.md`）

---

## 自動化しないこと

- **無人起票はしない**。手順 4 の確認を挟む
- **実装・ブランチ作成はしない**（`/issue-start` の役割）
- **既存 Issue の本文をユーザー確認なしに書き換えない**（分割時の元 Issue も同様。元 Issue を親Issue に転用するか、クローズするかはユーザーに確認する）
