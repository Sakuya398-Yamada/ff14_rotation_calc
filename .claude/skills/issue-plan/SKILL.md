# Issue計画スキル（/issue-plan）

入力: **$ARGUMENTS**

ユーザーの要望を、`/issue-start` で 1 回に回せる粒度の GitHub Issue に落とし込み、ユーザー確認を挟んで起票する。**このスキルでは実装・ブランチ作成を行わない**。

## 使い方

```
/issue-plan ユーザー設定画面を追加したい
/issue-plan #12
/issue-plan
```

- 入力が要望の文章なら、それを起点に分割案を作る
- 入力が Issue 番号なら、その Issue が大きすぎる前提で **既存 Issue の分割** を行う（`/issue-start` Phase 1 の粒度チェックから誘導される経路）
- 入力が無ければ、手順 1 の質問から始める

## 判断基準

- **粒度・依存関係・親Issue**: 既定の粒度は `.claude/rules/git-conventions.md`「粒度」。分ける／分けないの判定と親Issue・sub-issue の扱いは後述「粒度の判定」（正本）
- **本文の構成**: `.claude/rules/git-conventions.md`「Issue のタイトルと本文」の見出し構成（背景・目的 / 要件（やること・やらないこと）/ 完了条件（DoD）/ 未確定事項）。Issue は実装の仕様書になるので、完了条件は検証可能な形で書く
- **タイトル・ラベル**: `<ラベル名>: <簡潔な説明>`、ラベルは `feature` / `bug` / `refactor` / `docs` のいずれか
- **GitHub 操作**: `.mcp.json` の GitHub MCP（`github-mcp-server` バイナリ、`.claude/rules/mcp-setup.md`）。未接続時は `gh` CLI（`/c/Program Files/GitHub CLI/gh.exe`）、それも無ければ整形済み本文を提示して起票を依頼する

## 粒度の判定

既定（目的 1 つ・1 セッションで完走できる量・単独で検証可能・独立性）は `.claude/rules/git-conventions.md`「粒度」。分けるかどうかは以下で判定する。

| 分ける（複数 Issue にする） | 分けない（1 Issue に保つ） |
|---------------------------|--------------------------|
| 「やること」に目的の異なる項目が並ぶ（「○○を追加し、ついでに△△を直す」） | 片方だけ入れると動作しない・検証できない（型定義とその唯一の利用箇所など） |
| 層ごとに単独で検証できる（DB → API → UI をそれぞれ動作確認できる） | 層をまたいでも 1 画面・1 機能として縦に切った方が検証しやすい |
| 片方が先に完了しないともう片方の設計が決まらない（依存順に分け、後続に `依存: #N`） | 分けた片方が DoD 1 個・差分数十行で、PR として意味を成さない |
| 完了条件が 7 個を超える／ラベルが複数（`feature` と `refactor` 等）にまたがる | ― |

迷ったら **「このIssueのPRだけをマージしても、壊れず・単独で説明できるか」** で判定する。Yes なら粒度は適切。

- 先に別 Issue の完了が必要な場合は、本文の「## 関連Issue」に `依存: #N` と書く（`/issue-start` Phase 1 で依存先が未完了なら着手前に確認される）
- 1 つの要望を 3 件以上に分割したときは、進捗管理用の **親Issue** を作ってよい。親Issue 自体は実装対象ではないので `/issue-start` しない
- 親子関係は GitHub の **sub-issue** で紐づける（GitHub MCP: `issue_write` の `parent_issue_number`、既存 Issue なら `sub_issue_write`）。親Issue には進捗が自動集計される。sub-issue を作れない環境（`gh` CLI フォールバック等）では、親本文のタスクリスト（`- [ ] #N <タイトル>`）と子本文末尾の `親Issue: #N` で代用する。`/issue-start` がスコープ外問題で起票する子Issue も同じ扱い

## 手順

### 1. 要望の把握（不足があれば質問して止まる）

以下が揃っているかを確認し、足りなければ **推測せずに質問する**。質問は 1 回にまとめ、可能なら選択肢を添える（`AskUserQuestion` が使えるなら選択式で）。

| 項目 | 確認内容 |
|------|---------|
| 背景・目的 | なぜ必要か。誰が困っているか |
| やりたいこと | 期待する振る舞い・成果物 |
| やらないこと | 今回のスコープから外すもの |
| 制約 | 期限・互換性・対象環境・使ってよい技術 |
| 完了の判断基準 | 何が確認できれば完了か |

入力が既存 Issue 番号の場合は、`issue_read`（method: `get` / `get_comments`）で本文・コメントを取得し、それを要望として扱う。

### 2. 現状の把握（軽量に）

1. **重複・関連 Issue の検索**: `search_issues`（`owner` / `repo` を指定、query は自然文）で検索する。重複候補があればリンクを提示し、新規起票ではなく **既存 Issue へのコメント追記・本文更新** を提案する
2. **技術前提の実在確認**: 要望に「○○を新規実装する」のような技術前提があれば `Grep` で実在を確認する（`/issue-start` Phase 1.5「乖離チェック」と同じ）。既に存在すればスコープを縮める
3. **既存構造の把握（必要な場合のみ）**: 大きめの機能で、既存構造を知らないと分割できない場合に限り、`code-explorer` を **1 個** 起動する。返却量の上限（例: 「`file:line` と 3 行以内の要約のみ、合計 200 行以内」）を明記する（`.claude/rules/context-efficiency.md`）。全読みはしない

### 3. 分割案の作成

1. 「粒度の判定」表に従って Issue 候補に分割する
2. **依存順に並べる**（基盤 → 利用側）。並列に進められる候補はそう明記する
3. 各候補に以下を揃える：
   - タイトル（`<ラベル名>: <簡潔な説明>`）とラベル
   - 背景・目的（1〜2 文）
   - やること／やらないこと
   - 完了条件（検証可能なチェックリスト。「やること」の言い換えではなく、動作確認・テストの観点で書く）。数値目標（行数・件数・時間など）を置くときは、現状値を測って本文に添え、スコープ内で届くかを確かめる
   - 依存（`依存: #N`。まだ番号が無い候補への依存は「候補 2 に依存」と書き、起票時に実番号へ置き換える）
   - 未確定事項（あれば）。`## 未確定事項` に 1 項目 1 行で書き、次の 2 つを書き分ける
     - ユーザーが決めること（要件・仕様の分岐で、本文と既存コードからは決められないもの）: `[要確認] 要ユーザー確認: <何を決めるか>`。日次の無人実装（`weekday-issue-start`）は、この表記の項目がある Issue を選ばない。`## 要件` など別の節に「ここで決める」と書くと選定をすり抜けるので、決定待ちはこの節に置く
     - 調べれば分かる確認（コード・公式資料で答えが出るもの、`/issue-start` Phase 4 の設計で選べるもの）: `[要確認] <何を確かめるか>`（「要ユーザー確認」は付けない）
   - 手がかり（分かる範囲で関連ファイルや既存の類似実装。`/issue-start` の探索が速くなる）
4. 候補が **3 件以上** になったら、進捗管理用の **親Issue** を作るかを選べるようにする（「粒度の判定」）

### 4. ユーザー確認（必須）

以下のフォーマットで提示し、承認を得るまで起票しない。

```
【Issue計画】要望: <1行要約>
重複・関連Issue: なし / 既存 #NN（→ 統合 or 参照）

候補1  <ラベル>: <タイトル>
  目的: <1〜2文>
  やること: <箇条書き> ／ やらないこと: <箇条書き>
  DoD: - [ ] ... - [ ] ...
  依存: なし

候補2  <ラベル>: <タイトル>
  ...
  依存: 候補1

親Issue: 作る（<タイトル>） / 作らない
推奨着手順: 候補1 → 候補2（候補3 は並列可）

起票しますか？
 [Y] この内容で全件起票
 [E] 編集する（候補番号と修正内容を指定。「候補1と2をまとめて」のような粒度の修正も可）
 [N] 起票しない（計画の提示のみ）
```

- [E] の場合は修正を反映して **再提示** し、改めて Y/E/N を取る
- 一部の候補だけ起票したい場合は候補番号を指定してもらう

### 5. 起票

1. **親Issue を作る場合は先に作る**（`issue_write`、method: `create`）。ラベルは子 Issue の多数派（例: `feature`）。本文に目的と「このIssueは進捗管理用。`/issue-start` の対象にしない」を明記する。sub-issue の進捗は GitHub が自動集計する
2. 子 Issue を **依存順に** 1 件ずつ起票する（`issue_write`、method: `create`）。親がある場合は `parent_issue_number` に親の番号を渡して **sub-issue として** 作る。本文は `git-conventions.md`「Issue のタイトルと本文」の構成に揃える
3. 後続 Issue の `依存: #N` は、先行 Issue の実番号に置き換えてから起票する
4. ラベルを付ける（権限が無ければ省略してよい。`/issue-start` Phase 2 で判定される）
5. sub-issue を作れない環境（`gh issue create` が `--parent` を持たない版など）では、親本文のタスクリスト `- [ ] #N <タイトル>` と各子 Issue 末尾の `親Issue: #<親番号>` で代用する（`issue_write` method: `update` / `gh issue edit`）
6. **起票に失敗した場合**（権限・ネットワーク等）: 整形済み本文を提示して手動起票を案内する。`gh issue create --title ... --label ... --body-file <tmp>` へのフォールバックも可

### 6. 結果の提示

- 起票した Issue の一覧（番号・タイトル・依存）と推奨着手順を提示する
- 次のアクションとして `/issue-start #<最初に着手するIssue>` を案内する
- このセッションで **ワークフロー自体** への気づき（粒度規約の曖昧さ、質問項目の不足等）があれば、`.claude/rules/workflow-feedback.md` に従いユーザー確認を挟んで知見ボードに追記する

---

## 自動化しないこと

- **無人起票はしない**。手順 4 の確認を挟む
- **実装・ブランチ作成はしない**（`/issue-start` の役割）
- **既存 Issue の本文をユーザー確認なしに書き換えない**（分割時の元 Issue も同様。元 Issue を親Issue に転用するか、クローズするかはユーザーに確認する）
