# weekly

あなたはこのリポジトリの週次 Issue 起票ルーティンです。**無人実行**なので、ユーザーへの質問はせず、判断できないものは起票せずに実行報告へ回してください。

- 実行環境: クラウドのスケジュールタスク。実行のたびにリポジトリを clone し、その直下から、`main` から切った作業ブランチ（`claude/*` など）で起動する
- このリポジトリの名前は書かない。`gh api` の `{owner}/{repo}` は、`gh` がカレントの git リモートから埋める。git と `gh` はリポジトリ直下で、`-C` を付けずに打つ
- メモ inbox と知見ボードからの起票は、日次の `daily-triage`（`.claude/routines/daily-triage.md`）が行う。このルーティンでは扱わない

## 共通ルール

1. リポジトリの `CLAUDE.md` と `.claude/rules/*.md` に従う。Issue の様式・ラベル・粒度は `.claude/rules/git-conventions.md`
2. 最初に `git fetch origin` し、`git show origin/main:.claude/rules/routines.md` を読む（このファイルは `paths:` 付きなので、`git show` で読む手順書では自動で読み込まれない）。実行ログ Issue の番号は「管理用の Issue」にある。`<...>` のプレースホルダーのままなら、`meta: ルーティン実行ログ` の Open Issue を探して使う
3. コードやデータは `origin/main` の内容を読む（`git show origin/main:<path>` / `git grep <pattern> origin/main -- <path>`）。**作業ツリーの変更・ブランチ作成・コミット・PR はしない**
4. GitHub 操作は GitHub MCP を使い、使えなければ REST の `gh api repos/{owner}/{repo}/...` にフォールバックする。`gh issue` / `gh pr` などのサブコマンドは GraphQL を使うので、クラウドセッションでは 403 になる。使わない（`.claude/skills/issue-start/pitfalls-cloud.md`「クラウドセッションでは gh の GraphQL 系が使えない」）
5. 書き込みは `.claude/rules/routines.md`「事前に承認した書き込み」の `weekly` の分だけ（起票と実行報告）。既存の Issue・コメントの編集、既存の Issue のラベルの追加・削除はしない。テンプレート元（`.claude/template-version` の `repo`）への起票・コメントもしない
6. 起票のきまり
   - 起票の前に重複を確かめる（Open / Closed の両方を検索する）。同じ目的の Issue があれば起票しない
   - 本文は `## 背景・目的` / `## 要件`（やること・やらないこと）/ `## 完了条件（DoD）` / `## 未確定事項`（あれば）/ `## 関連Issue` で構成し、末尾に下のフッターを付ける
   - ラベルは種別を 1 つだけ付ける（系統2 の系統が別のラベルを決めていれば、それに従う）。`priority:*` は付けずに起票する（日次の `daily-triage` が次の実行で付ける。判定を 1 か所にまとめるため。`daily-triage` を登録していなければ、人が `/issue-priority` で付ける）
   - 起票は全系統を合わせて **1 回の実行で 10 件まで**（既定値。プロジェクトで変えてよい）。超えた分は実行報告の「見送り」に挙げる

   ```
   ---
   _週次 Issue 起票ルーティン（<系統名>）により自動起票_
   ```

## 起票前のバックログ確認

系統1 に入る前に 1 回だけ数える。数は実行報告の「その他」に書く。

1. **バックログ（Open の作業 Issue）** を、`origin/main` の `.claude/routines/daily-triage.md`「1. バックログを数える」の数え方で数える（数え方と上限の正本はそちら。`git show origin/main:.claude/routines/daily-triage.md` で読む）
2. **上限以上なら、系統1（コードスキャン）を見送る**（手順全体を飛ばす）。実行報告の「見送り」に「バックログ上限に到達（N 件）」と書く。系統2 は、外部が起点の系統（外部の仕様の更新の監視など）は見送らず、それ以外は系統1 と同じく見送る
3. 無人実装を使うプロジェクト（リポジトリにラベル `routine-ok` がある。`/issue-priority`「無人実装を使うか」）だけ、無人実装の Open PR も数える（数え方は `origin/main` の `.claude/routines/weekday-issue-start.md`「1. 事前点検（安全弁）」手順 2 の、自分の Open PR の見分け方。手順書が無ければ数えず、実行報告に「数えられず（手順書が無い）」と書く）。数は実行報告に書くだけで、見送りの判定には使わない。使わないプロジェクトでは数えない

## 系統1: コードスキャン

- **対象**: `src/client/`
- **観点**（前例の Issue があれば添えると、確度の判断に効く）:
  - ジョブ間のデータ不整合（同じ種類の値が一部のジョブだけ異なる。前例 #350）
  - 定義と参照の食い違い（定義されているのに付与・消費されないバフなど。前例 #349）
  - 実装済みジョブ間で欠けているデータ項目（他のジョブにはある AoE データが無いなど。前例 #321）
  - ユニットテストの無いジョブ固有ロジック・計算式（前例 #303 / #333）

1. 対象が `<...>` のプレースホルダーのままか、観点がすべて `<...>` のままなら、この系統は飛ばし、実行報告に「対象・観点が未記入」と書く。`<...>` のままの観点だけは使わない
2. 探索は `code-explorer` サブエージェントに委譲し、`file:line` 付きの要約だけを受け取る（返却は合計 200 行以内と指定する）。対象は `origin/main` の上の対象のディレクトリ
3. 根拠を `file:line` で示せる、確度の高いものだけを **最大 3 件**（既定値）起票する。仕様の推測が入る部分は `## 未確定事項` に書く
4. **人のゲート**: 起票する Issue の `## 未確定事項` に、次の 1 行を必ず入れる（ほかに未確定事項が無くても、節を作って入れる）。この行がある Issue は、決定待ちの項目があるので、無人実装の候補（`.claude/skills/issue-priority/routine-candidates.md`「候補条件」）にならない。無人実装されるのは、人が内容を確かめてこの行を消し、`routine-ok` を付けたあと。系統1 では必ず付ける。系統2 で付けるかは、各系統の定義に従う（下の「系統2」。`daily-triage` がメモ inbox・知見ボードから起票する Issue は、人が起点なので付けない）

   ```
   - [要確認] コードスキャンによる自動起票のため仕様の推測を含む。内容を確認したらこの行を消す
   ```

5. フッターの系統名: `コードスキャン系統`

## 系統2: プロジェクト固有の系統（任意）

外部の仕様・データの更新の監視のように、このプロジェクトだけの起票の系統があれば、この節に足す。無ければ飛ばす。足すときは、次を書く（1 系統ごとに `### 系統2-1: <名前>` のような見出しにする）。

- 何を調べるか（`origin/main` のどのファイルの何の値か、外部のどの URL か）
- 新しいものがあるかの判定と、何もしない条件（新しいものが無い、同じ対象の Issue が既にある）
- 起票する Issue の形（タイトルの例、本文の要件と完了条件に入れること、ラベル）。1 回の実行で起票する件数
- フッターの系統名
- 外部が起点の系統なら、系統1 の人のゲートの行は入れなくてよい。仕様の推測が入るなら入れる

### 系統2-1: パッチ情報監視

外部（パッチノート）が起点の系統なので、バックログ上限でも見送らず、人のゲートの行も入れない。

1. **現在の追従版を調べる**: `origin/main` の `src/client/data/*-skills.ts` の冒頭コメントにある「パッチノートの PvE ジョブ調整は X.Y まで反映済み」を読む（ジョブごとに違えば最も古い版を基準にする）
2. **新しい版があるか調べる**: Lodestone のパッチノート一覧 `https://jp.finalfantasyxiv.com/lodestone/special/patchnote_log/` に、追従版より新しい版があるか調べる。WebFetch の要約に頼らず、生 HTML を取得してタグを除去してから読む
3. 新しい版が無い、または同じ版を対象にしたパッチ検証 Issue が既にあれば、この系統は何もしない
4. 新しい版があれば、**パッチ検証 Issue を 1 件**起票する（前例 #304。ラベルは `question`）。ジョブ別の修正 Issue はこの系統では起票せず、検証 Issue の作業中に不一致ごとに子 Issue として起票する（#304 → #407〜#412 の流れ）
   - タイトル例: `question: パッチX.Yのジョブ調整と公式ジョブガイドに実装済みジョブのスキルデータが追従しているか検証する`
   - 本文の要件と完了条件には、次の 2 つを**両方**含める。パッチノートは差分しか分からないため、①だけではデータがもともとずれているケースを見逃す
     - ① 対象版のパッチノート（「バトル関連」から、目次でその次に並ぶ見出し（「PvP全般」など）の手前まで）から、実装済みジョブ（`*-skills.ts` があるジョブ）の PvE 調整を抽出し、データに反映済みか確かめる
     - ② 実装済みジョブごとに、公式ジョブガイドの PvE 欄（「PatchX.Y…のPvP全般のアップデート内容は」の行より前）とスキルデータを全件照合する
   - 本文に「手順・判定基準の詳細は `.claude/skills/issue-start/phases/01-external-data.md`「パッチ追従の検証（定型）」に従う」と書く
   - DoD に「各ジョブの `*-skills.ts` 冒頭コメントの追従版（X.Y まで反映済み）と、既知の差分の子 Issue 番号を更新する」を含める
   - ルーティンが調べた範囲（確認した URL、見つかった版、PvE 調整の有無の見立て）は `### 調査の経緯` として本文に残してよい。推測した数値は書かない
5. フッターの系統名: `パッチ情報監視系統`

## 系統3: 優先度の付け直し案

起票はしない。系統1・2 で起票した Issue も対象に含めるため、最後に行う。起票しないので、バックログ上限による見送りの対象にもしない。

1. `origin/main` の `/issue-priority` skill（`git show origin/main:.claude/skills/issue-priority/SKILL.md`。skill が参照する `.claude/skills/issue-priority/routine-candidates.md` も同じく読む）の「無人実装を使うか」と手順 1〜4 を、引数なし（Open Issue 全件）として行う。本文とコメントは、手順 2 のとおり `general-purpose` エージェントに任せ、要約だけを受け取る
2. 進行中ではなく、`priority:*` が付いていて案と違う Issue を、「現在 → 案」と理由（skill 手順 4「priority の根拠」の言い回し）で並べる。`priority:*` が無い Issue は件数だけ数える（日次の `daily-triage` が付ける）
3. **ラベルは変えない**（付与も付け替えもしない）。付け直すかは、人が実行報告を読んで `/issue-priority` で決める

## 実行報告

最後に、次の形式で報告する。報告の本文は、実行ログ Issue にもコメントとして投稿する（**1 実行 1 コメント**。起票が 0 件の実行も投稿する）。投稿できなければ（GitHub MCP も gh も使えない等）、セッションに報告を出すだけにする。無人実装を使わないプロジェクトでは、「無人実装の Open PR 数」の行を出さない。

```
## weekly 実行報告（YYYY-MM-DD）
### 系統1 コードスキャン
- 起票: #N タイトル（根拠 file:line）… ／ なし ／ 飛ばした（対象・観点が未記入、バックログ上限）
### 系統2 プロジェクト固有の系統
- パッチ情報監視: 追従版 X.Y ／ 最新パッチノート X.Y ／ 起票: … ／ なし
### 系統3 優先度の付け直し案（ラベルは変えていない。付け直すなら /issue-priority）
- #N タイトル: 現在 low → 案 high（理由）… ／ なし
- priority 未付与: N 件（次の daily-triage が付ける）
### その他
- 見送り（上限超過・重複・バックログ上限）: … ／ なし
- バックログ（Open の作業 Issue、上限は daily-triage.md「1.」）: N 件
- 無人実装の Open PR 数: N 件
- テンプレート更新: SessionStart のバナーに更新ありと出ていれば「あり（vOLD → vNEW）」と書くだけで、起票はしない
```
