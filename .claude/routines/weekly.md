# weekly-issue-intake

あなたは FF14 Rotation Calculator の週次 Issue 起票ルーティンです。**無人実行**なので、ユーザーへの質問はせず、判断できないものは起票せずに実行報告へ回してください。

- GitHub: `Sakuya398-Yamada/ff14_rotation_calc`
- 実行環境: クラウドのスケジュールタスク。実行のたびにリポジトリを clone し、その直下から、`main` から切った `claude/*` の作業ブランチで起動する

系統1（メモ inbox #305）と系統2（知見ボード #195 の棚卸し）は、日次 `daily-triage`（`.claude/routines/daily-triage.md`）へ移した（#502）。系統の番号は参照を保つため 3〜5 のまま使う。

## 共通ルール

1. リポジトリの `CLAUDE.md` と `.claude/rules/*.md` に従う。Issue の様式・ラベル・粒度は `.claude/rules/git-conventions.md`
2. 最初に `git fetch origin` する（git は起動したリポジトリ直下で、`-C` を付けずに打つ）。コードやデータは `origin/main` の内容を読む（`git show origin/main:<path>` / `git grep <pattern> origin/main -- <path>`）。**作業ツリーの変更・ブランチ作成・コミット・PR はしない**
3. GitHub 操作は GitHub MCP を使い、使えなければ REST の `gh api repos/Sakuya398-Yamada/ff14_rotation_calc/...` にフォールバックする。`gh issue` / `gh pr` などのサブコマンドは GraphQL を使うので 403 になる。使わない（`.claude/skills/issue-start/pitfalls.md`「クラウドセッションでは gh の GraphQL 系が使えない」）
4. **起票前に必ず重複チェック**する（Open / Closed の両方を検索）。同じ目的の Issue があれば起票しない
5. 起票する Issue の本文は `## 背景・目的` / `## 要件`（やること・やらないこと）/ `## 完了条件（DoD）` / `## 未確定事項`（あれば）/ `## 関連Issue` で構成し、末尾に次のフッターを付ける。ラベルは種別 1 つ＋ `priority:*` 1 つ

   ```
   ---
   _週次 Issue 起票ルーティン（<系統名>）により自動起票_
   ```

6. 起票は全系統合わせて **1 回の実行で 10 件まで**。超えた分は実行報告の「見送り」に挙げる
7. **新規コメントは投稿しない**。例外は「実行報告」節で定める実行ログ Issue #448 への実行報告だけ（`.claude/rules/workflow-feedback.md`「自動化しないこと」で事前承認済み）。既存コメントの編集もしない
8. テンプレート元（`Sakuya398-Yamada/issue-driven-dev-starter`）への起票・コメントはしない

## 起票前のバックログ確認

系統3 に入る前に 1 回だけ数える。数は実行報告の「その他」に書く。

1. **バックログ（Open の作業 Issue）** を、`origin/main` の `.claude/routines/daily-triage.md`「1. バックログを数える」の数え方で数える（数え方と上限の正本はそちら。`git show origin/main:.claude/routines/daily-triage.md`）
2. **上限以上なら系統4（コードスキャン）を見送る**（手順全体を飛ばす）。実行報告の「見送り」に「バックログ上限に到達（N 件）」と書く。系統3（パッチ情報監視）は外部が起点なので見送らない
3. **無人実装の Open PR** も数える: Open PR のうち、本文末尾に `_スケジュール実行（weekday-issue-start）による無人実装_` のフッターがあるもの。数は実行報告に書くだけで、見送りの判定には使わない

## 系統3: パッチ情報監視

1. **現在の追従版を調べる**: `origin/main` の `src/client/data/*-skills.ts` の冒頭コメントにある「パッチノートの PvE ジョブ調整は X.Y まで反映済み」を読む（ジョブごとに違えば最も古い版を基準にする）
2. **新しい版があるか調べる**: Lodestone のパッチノート一覧 `https://jp.finalfantasyxiv.com/lodestone/special/patchnote_log/` に、追従版より新しい版があるか調べる。WebFetch の要約に頼らず、生 HTML を取得してタグを除去してから読む
3. 新しい版が無い、または同じ版を対象にしたパッチ検証 Issue が既にあれば、この系統は何もしない
4. 新しい版があれば、**パッチ検証 Issue を 1 件**起票する（前例 #304。ラベルは `question` と `priority:*`）。ジョブ別の修正 Issue はこの系統では起票せず、検証 Issue の作業中に不一致ごとに子 Issue として起票する（#304 → #407〜#412 の流れ）
   - タイトル例: `question: パッチX.Yのジョブ調整と公式ジョブガイドに実装済みジョブのスキルデータが追従しているか検証する`
   - 本文の要件と完了条件には、次の 2 つを**両方**含める。パッチノートは差分しか分からないため、①だけではデータがもともとずれているケースを見逃す
     - ① 対象版のパッチノート（「バトル関連」〜「PvP全般」の手前）から、実装済みジョブ（`*-skills.ts` があるジョブ）の PvE 調整を抽出し、データに反映済みか確かめる
     - ② 実装済みジョブごとに、公式ジョブガイドの PvE 欄（「PatchX.Y…のPvP全般のアップデート内容は」の行より前）とスキルデータを全件照合する
   - 本文に「手順・判定基準の詳細は `.claude/skills/issue-start/phases/01-issue-analysis.md`「パッチ追従の検証（定型）」に従う」と書く
   - DoD に「各ジョブの `*-skills.ts` 冒頭コメントの追従版（X.Y まで反映済み）と、既知の差分の子 Issue 番号を更新する」を含める
   - ルーティンが調べた範囲（確認した URL、見つかった版、PvE 調整の有無の見立て）は `### 調査の経緯` として本文に残してよい。推測した数値は書かない
5. フッターの系統名: `パッチ情報監視系統`

## 系統4: コードスキャン

1. 探索は `code-explorer` サブエージェントに委譲し、`file:line` 付きの要約だけを受け取る（返却は合計 200 行以内と指定する）。対象は `origin/main` の `src/client/`
2. 次の観点で起票候補を探す
   - ジョブ間のデータ不整合（同じ種類の値が一部のジョブだけ異なる。前例 #350）
   - 定義と参照の食い違い（定義されているのに付与・消費されないバフなど。前例 #349）
   - 実装済みジョブ間で欠けているデータ項目（他のジョブにはある AoE データが無いなど。前例 #321）
   - ユニットテストの無いジョブ固有ロジック・計算式（前例 #303 / #333）
3. 根拠を `file:line` で示せる、確度の高いものだけを **最大 3 件**起票する。仕様の推測が入る部分は `## 未確定事項` に書く
4. **人のゲート**: 起票する Issue の `## 未確定事項` に、次の 1 行を必ず入れる（他に未確定事項が無くても節を作って入れる）。この文言の項目がある Issue は、日次の無人実装（`weekday-issue-start`）の選定からも、`daily-triage` が出す `routine-ok` を付ける候補からも外れる。無人実装されるのは、人が内容を確認してこの行を消し、`routine-ok` を付けたあと。この行を付けるのは系統4 だけ（系統3 は外部が起点。`daily-triage` が起票するメモ inbox と知見ボードの Issue は人が起点）

   ```
   - [要確認] 要ユーザー確認: コードスキャンによる自動起票のため仕様の推測を含む。内容を確認したらこの行を消す
   ```

5. フッターの系統名: `コードスキャン系統`

## 系統5: 優先度の付け直し案

起票はしない。系統3・4 で起票した Issue も対象に含めるため最後に行う。起票しないので、バックログ上限による見送りの対象にもしない。

1. `origin/main` の `/issue-priority` skill（`git show origin/main:.claude/skills/issue-priority/SKILL.md`）の手順 1〜4 を、引数なし（Open Issue 全件）として行う。本文とコメントは手順 2 のとおり `general-purpose` エージェントに任せ、要約だけ受け取る
2. 進行中ではなく、`priority:*` が付いていて案と違う Issue を「現在 → 案」と理由で並べる。`priority:*` が無い Issue は件数だけ数える（日次 `daily-triage` が付ける）
3. **ラベルは変えない**（付与も付け替えもしない）。付け直すかは、人が実行報告を読んで `/issue-priority` で決める

## 実行報告

最後に、次の形式で報告する。報告本文は実行ログ Issue #448（`meta: ルーティン実行ログ`）にもコメントとして投稿する（**1 実行 1 コメント**。起票が 0 件の実行も投稿する。この投稿は `.claude/rules/workflow-feedback.md`「自動化しないこと」の例外として事前承認済み）。投稿できなければ（GitHub MCP も gh も使えない等）、従来どおりセッションに報告を出すだけにする。

```
## weekly-issue-intake 実行報告（YYYY-MM-DD）
### 系統3 パッチ情報監視
- 追従版: X.Y ／ 最新パッチノート: X.Y ／ 起票: …
### 系統4 コードスキャン
- 起票: …
### 系統5 優先度の付け直し案（ラベルは変えていない。付け直すなら /issue-priority）
- #N タイトル: 現在 low → 案 high（理由）… ／ なし
- priority 未付与: N 件（次の daily-triage が付ける）
### その他
- 見送り（上限超過・重複・バックログ上限）: …
- バックログ（Open の作業 Issue、上限は daily-triage.md「1.」）: N 件
- 無人実装の Open PR 数: N 件
- テンプレート更新: SessionStart のバナーに更新ありと出ていれば「あり（vOLD → vNEW）」と記載するだけで、起票はしない
```
