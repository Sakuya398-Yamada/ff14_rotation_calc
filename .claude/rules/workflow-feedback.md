# ワークフロー改善の知見ボード

`.claude/rules/` 配下のため起動時に自動で読み込まれる。
`/issue-start` セッションで得た **ワークフロー改善の気づき** を累積する専用Issueの運用規約と、テンプレート元との双方向のやり取り（**知見の還元** と **テンプレート更新の取り込み**）の判定基準。手順そのものは常駐させず、`/issue-start` の phases と `/template-update` skill に置いてある（各節の「手順の正本」）。

## 知見ボードIssue

- **タイトル**: `meta: ワークフロー改善の知見ボード`
- **ラベル**: `meta`

- **URL**: https://github.com/Sakuya398-Yamada/ff14_rotation_calc/issues/195

## 知見ボードの読み方

#195 のコメントは GitHub MCP の `issue_read`（`get_comments`）で丸読みしない。全コメントがユーザー情報・URL 等のメタデータ込みでセッションに入り（2026-10 時点で 58 件・生 JSON 約 220KB）、必要なのは多くの場合「未回収の知見の一覧」か「特定キーワードの過去の知見」だけだからである。代わりに `.claude/scripts/knowledge-board.cjs` で必要な分だけ出力する。

```bash
node .claude/scripts/knowledge-board.cjs open            # 未回収の知見を 1 件 1 行（ID・日付・作業Issue・重要度・還元先・気づきの冒頭）
node .claude/scripts/knowledge-board.cjs grep <pattern>  # 本文を検索（大文字小文字を区別しない正規表現）。当たったコメントの ID・日付・作業Issue・回収状況と該当行だけ
node .claude/scripts/knowledge-board.cjs show <id>       # 1 件の本文
```

- 毎回 `gh api --paginate` で取り直し、生 JSON を OS の一時ディレクトリ（`knowledge-board-195.json`）に保存する。続けて何度も読むときは `--cached` を付けると取り直さずに保存済みの JSON を使う
- 未回収の判定は後述「回収済み判定の正」の 2 形式のマーカーで行う
- コメントの編集（✅ マーカー追記・還元先の更新）に要るコメント ID は `open` / `grep` の先頭列から取る

## テンプレート元の情報

本プロジェクトのワークフロー（`CLAUDE.md` / `.claude/`）のノウハウは、汎用テンプレート [issue-driven-dev-starter](https://github.com/Sakuya398-Yamada/issue-driven-dev-starter) の Claude Code 版（`template/`）として切り出されている。本プロジェクトはテンプレートの**出自側**だが、以降はテンプレート側を正として知見を還元し、改善を取り込む運用にする。テンプレート元との接点は `.claude/template-version`（`repo=<owner/repo>` と `version=vX.Y.Z`。版はテンプレート元の Release タグと同一書式）に集約してある。`version` は「還元・更新の基準としてこの版と整合している」ことを示し、テンプレート更新を取り込んだら更新する。

## 何を書くか

ワークフロー全体（`/issue-start` / `/issue-plan` の手順、`.claude/rules/*`、`CLAUDE.md`、hooks、skills、MCP 運用等）への気づきを集約する。

| 集約対象 | 集約対象外 |
|---------|-----------|
| ワークフローの冗長・曖昧さ | 個別Issueの実装メモ（→ 当該Issueのコメント） |
| スキル定義の改善余地 | FF14 仕様そのもの（→ 該当Issueや新規Issue） |
| 規約・ガードレール追加候補 | コード上の個別バグ（→ 別Issueとして起票） |
| MCP ツール運用のハマりどころ | コードスタイルの好み |

## いつ書くか

`/issue-start` **Phase 8 の最後**（個別Issueへの実装メモ記録が終わった後）に、その回のセッションで見つけた気づきがあれば書き込む。Phase 5〜7 で気づいたことはその場で直さず短文メモに留め、Phase 8 で棚卸しする。

- **気づきが無い場合はスキップしてよい**（「特になし」と明示コメントしなくてよい）
- **ユーザー確認を挟んでから書き込む**（無人書き込みはしない）
- 手順の正本: `phases/08-issue-recording.md` 手順 5（候補の提示フォーマットとコメント本文テンプレート）

## 重要度の判定基準

| 重要度 | 目安 |
|--------|------|
| **High** | 毎セッション再発する／セッション失敗の直接原因／ガードレール追加で即座に解消できる |
| **Medium** | 数回に一度発生する／手順が冗長・曖昧で毎回判断コストが掛かる |
| **Low** | 1回限りの気づき／将来あると便利レベル／ユーザー影響が軽微 |

## テンプレート元への還元（upstream feedback）

知見ボードに書いた気づきのうち **テンプレート汎用のもの** は、本プロジェクト内で閉じさせず、**テンプレート元リポジトリの Issue として起票**する。テンプレート側はその Issue を通常の `/issue-start` フローで精査・反映し、リリースを切る。リリースは後述の更新チェックで本プロジェクトにも戻ってくる。

手順の正本: `phases/08-issue-recording.md` 手順 6（抽象化 → 重複チェック → ユーザー確認 → 起票 → 元コメントへの印）。

### 還元する / しないの判定

| テンプレート汎用（還元する） | プロジェクト固有（還元しない） |
|---------------------------|----------------------------|
| `/issue-start` の手順・Phase 構成・ユーザー確認の粒度 | `tech-stack.md` / `coding-standards.md` / `testing-conventions.md` / `playwright-mcp` skill の中身 |
| `git-conventions.md` / `context-efficiency.md` / `workflow-feedback.md` / `documentation-policy.md` の規約そのもの | 本プロジェクト固有の MCP 構成・`settings.json` の権限 |
| hooks / agents / skills の挙動・判定ロジック・出力上限 | FF14 仕様・React / Vite / Prisma 等に閉じたハマりどころ（「言語別の例が欲しい」のように一般化できる要望は汎用） |
| Issueテンプレート・セットアップ手順・プレースホルダーの不備 | 定期ルーティン（`.claude/routines/`）等、本プロジェクトの運用都合による独自ルール |

迷ったら「**テンプレートを新規に使う別プロジェクトでも同じ問題が起きるか**」で判定する。起きるなら汎用。

### 還元 Issue に含めないもの

テンプレート元は **公開リポジトリ** である。以下は書かず、ワークフロー手順のレベルに抽象化する：

- 本プロジェクトのコード断片・ファイルパス・内部識別子・URL（FF14 のスキル名・ジョブ名等のドメイン固有語も含む）
- 顧客名・社内システム名・人名
- 認証情報・環境変数の値
- `#N` 形式の Issue / PR 番号（テンプレート元の番号として誤リンクされる。必要なら `owner/repo#N` 形式にする）

## テンプレート更新の取り込み（update check）

テンプレート元で改善がリリースされると、SessionStart hook（`.claude/hooks/session-start-info.sh`）が `.claude/template-version` の `version` と最新リリースタグを比較し、差があれば `## Template version` バナーに `⚠ Template update available` を出す。最新タグはセッション開始のたびに `git ls-remote` で取得し、取得に失敗したときだけ前回の結果（`$(git rev-parse --git-common-dir)/template-version-check`、worktree 共有）を使ってバナーに `(cached Nh ago; ...)` と付ける。

- **作業中の Issue のブランチでテンプレートを直接更新しない**（1 Issue = 1 PR）。更新は `refactor: テンプレートを vX.Y.Z に更新` Issue を起票し、独立した PR で取り込む
- 検知と更新用 Issue の起票の正本: `phases/01-issue-analysis.md` 手順 0.5（セッションで一度だけ聞く。Issue 本文に含める項目と、スケジュール実行の無人セッションでの扱いもここ）
- 取り込み（更新用 Issue の Phase 5）の正本: `.claude/skills/template-update/SKILL.md`（`/template-update`。3-way マージの定型手順と DoD を含む）

## 定期ルーティン（`.claude/routines/`）

週次 `weekly` と日次 `weekday-issue-start` の 2 つを Claude Desktop のスケジュールタスクに登録している。一覧・登録先との同期・実行ログの扱いは `.claude/rules/routines.md`（`paths:` で `.claude/routines/` 配下を触ったときだけ読み込む）。

## 棚卸し運用（週次ルーティンが正）

棚卸しは週次ルーティン（taskId **`weekly`**、毎週日曜 22:00 実行）**の系統2** が自動で行う。これを正の運用とする。手順の正本は `.claude/routines/weekly.md`「系統2: 知見ボード #195 の棚卸し」（未回収の知見を還元先で振り分けて昇格起票し、✅ マーカーを追記する。#195 への新規コメントとテンプレート元への還元はしない）。ルーティンで昇格した知見が `還元先: テンプレート汎用（未還元）` の場合は、下記「手動棚卸し」手順 4 としてユーザーが還元する。

### 手動棚卸し

ユーザーによる手動棚卸し（随時）も引き続き認める。手順は週次ルーティンと同じ：

1. `knowledge-board.cjs open` で未回収の知見を洗い出し、独立した改善Issue として昇格起票する（既存 Issue との重複は `search_issues`、過去の知見との重なりは `grep <キーワード>` で確かめる）
2. 元コメントへ ✅ マーカーを追記する
3. 昇格後Issueは通常の `/issue-start` フローで実装する
4. 実装した改善が **テンプレート汎用** で、まだ還元していなければ（元コメントの `還元先` が `テンプレート汎用（未還元）`、または `還元先` 未記入で汎用と判断できる）、`phases/08-issue-recording.md` 手順 6 でテンプレート元にも Issue を起票する（Phase 8 で還元済みなら不要）

## 回収済み判定の正

- **機械可読な正は「✅ Issue #<番号>」マーカー**とする。ルーティン・手動どちらの棚卸しでも、昇格したら元コメントに必ず付ける
- マーカーは 2 形式ある。どちらも回収済みとして扱う（`#\d+` だけで判定すると後者を取りこぼす）
  - 本プロジェクトの Issue に昇格: `✅ Issue #433 で対応`
  - テンプレート元の Issue で対応され、テンプレート更新で取り込み: `✅ Issue <owner/repo>#17 で対応（テンプレート更新で取り込み）`
- **Hidden as resolved（コメントの minimize）は任意の視覚整理**という位置づけ。REST API 経由ではコメントの minimize 状態は見えないため、**マーカー無しで Hidden だけされた知見はルーティンから未回収に見え、再昇格候補になり得る**（重複チェックで大半は弾かれるが、判定基準としては使わない）

## 自動化しないこと

- **無人コメント投稿はしない**: Phase 8 での知見ボードへの新規コメント投稿はユーザー確認（Y/E/N）を挟む
  - **例外**: 週次ルーティン（`weekly`）による既存コメントへの ✅ マーカー**追記編集**は事前承認済みで、無人実行してよい
  - **例外**: 両ルーティン（`weekly` / `weekday-issue-start`）が実行報告を実行ログ Issue #448 に**新規コメントとして投稿する**のは事前承認済み（#447。1 実行 1 コメント）。実行ログ Issue 以外への無人の新規コメント投稿は引き続き禁止
- **テンプレート元への無人起票はしない**: ローカル知見ボードへの承認とは別に、還元用に抽象化した本文で改めて確認（Y/E/N）を取る。週次ルーティン（`weekly`）にも還元処理は組み込まない
- **テンプレートの無人更新はしない**: 更新チェックは「通知して更新用 Issue の起票を提案する」までで、ファイルの書き換えは更新用 Issue の `/issue-start` で行う
- **知見ボードIssueを自動クローズしない**: 常時Open運用（実行ログ Issue #448 も同様。ログコメントの自動整理もしない）。**過去セッションからの遡及集約も行わない**（未来のセッションから運用する）
