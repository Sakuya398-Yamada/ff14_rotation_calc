# コンテキスト効率（context engineering）

`.claude/rules/` 配下のため起動時に自動で読み込まれる。

**目的**: コンテキストウィンドウに入れるトークンを「タスクに必要な、信号の濃い最小の集合」に保つ。窓が 1M トークンあっても、無関係な内容が増えるほどモデルの注意は薄まり、指示の取りこぼしや古い情報への引きずられ（context rot）が増える。読む量を減らすのは API エラー回避のためではなく、精度と判断の質のため。

## 原則

1. **必要なときに必要な分だけ読む（just-in-time）**: 全文理解を目的にせず、タスクに必要な行・関数・定義だけを読む
2. **探索→局所読みの二段構え**: まず Grep / Glob で該当箇所を特定し、その周辺だけ読む
3. **横断調査はサブエージェントに隔離する**: 3 ファイル以上を跨ぐ調査・大きなファイルの全体像把握・データフロー追跡は `code-explorer` に委譲し、要約だけを受け取る。生の探索ログを自分のコンテキストに入れない
4. **委譲するときは返却量の上限を書く**: 目的・スコープ・返却フォーマット・除外事項をプロンプトに含める（後述）
5. **読んだら要点を残す**: 大きなファイル・複雑なコードを読んだ直後に、理解した内容を 2〜3 行で要約してから次へ進む。あとで参照する判断は Issue コメント（Phase 8）に外部化する
6. **会話を引きずらない**: 1 セッション 1 Issue を基本にし、別の Issue に移るときは `/clear` する。長い実装で文脈が重くなったら Phase の切れ目で `/compact` する。`/context` で現在の消費量と読み込み済みファイルを確認できる
7. **迷走したら仕切り直す**: 同じ指摘で 2 回以上やり直しになったら、会話を続けて修正を重ねるより、`/clear` してから分かったことを 1 つのプロンプトにまとめて再開する方が速い（長い会話で初期の誤った前提から抜け出せなくなる傾向がある）

## ファイル読解の目安

数値は判断の目安であり、機械的な上限ではない。守るべきは「無関係なトークンを入れない」こと。

- **大きいファイル（目安 500 行超）** は丸読みしない。Grep で該当行を特定し、前後 30〜80 行だけ読む（`Read` の `offset` / `limit`、または `sed -n 'A,Bp'`）。構造だけ見たいときは `^(export |function |const |class |interface |type |def |fn )` 等を Grep して目次化する
- **同じファイルを同ターン内で繰り返し全読みしない**。必要なら該当行だけ再読する
- **画像・バイナリ・生成物（ビルド出力、lock ファイル、巨大な JSON）** は読まない
- **Grep** はまず `files_with_matches` で対象ファイルを絞り、内容確認は `content` + `-n` + `head_limit`（5〜30 程度）で量を抑える。広いパターン（`function` / `const`）は `type` や `glob` でスコープを絞る。前後行 `-C` は 3〜5 行に留める
- **Glob** の広いパターン（`src/**/*`）は最初の絞り込み専用。返却が 100 件を超えたらディレクトリや拡張子で分割する
- **ツールの選択は二の次**: `Read` でも `cat` / `sed -n` でも構わない。問題は「どの範囲を読むか」であって、どのツールで読むかではない。ただしファイル全体を標準出力に流す操作（`cat 大きなファイル`）は Read の全読みと同じなので避ける

本リポジトリの代表的な大きいファイル（2026-08 時点）：

| ファイル | 行数目安 | 読み方 |
|---------|---------|--------|
| `src/client/logic/resolve-timeline.ts` | ~1,600 | 分岐・状態遷移が密な高密度ロジック。関数名・バフ ID で Grep してから局所読み |
| `src/client/components/Timeline.tsx` | ~500（#283 で分割済み） | 該当コンポーネント・ハンドラを Grep してから局所読み |
| `src/client/data/*-skills.ts` / `*-buffs.ts` | 200〜750 | 構造が均質でトークン密度が低いので、必要なジョブのファイルは丸読みしてよい（テスト `__tests__/*.test.ts` も同様） |

- `src/client/assets/icons/**` の PNG は Read しない（ファイル名などの属性だけ把握すればよい）
- ファイル分割のリファクタは行数だけを理由にしない。props 配線だけが増える機械的な分割はせず、責務の境界が明確に切れる場合に限る（#283 の教訓）

## サブエージェント委譲

### 委譲すべきケース

- 3 ファイル以上の横断読みが必要
- 大きい 1 ファイル（目安 500 行超）の全体像把握が必要
- 複数コンポーネントを跨ぐデータフロー追跡
- 類似機能の洗い出し、影響範囲の特定

### 起動数の目安（タスクの複雑さに合わせる）

| タスク | 起動数 |
|-------|--------|
| 単純な修正・事実確認（1〜2 ファイル） | 自分で Grep + 局所読み。委譲しない |
| 1 領域の実装（数ファイル） | 1 個 |
| 複数領域を跨ぐ・比較観点が複数ある | 2〜3 個を並列。観点を分けて重複させない |

同じ観点で複数起動しても情報は増えず、コンテキストだけ増える。サブエージェントはチャット 1 往復の十数倍のトークンを使うので、`Grep` 1 回で分かることには使わない。

### 委譲時のプロンプトに含めるもの

1. **目的**: 何のための調査か（1 行）
2. **調査スコープ**: 対象ディレクトリ・ファイル・キーワード
3. **返却フォーマットと上限**: 例「`file:line` と 3〜5 行の要約のみ。合計 300 行以内」「関数シグネチャと挙動要約（各 3 行以内）のみ」「重要ファイル 5〜10 個のリスト付き」
4. **除外**: 引用不要なもの（例「import 文や型定義の列挙は不要」「コードの全文引用は不要」）

`code-explorer` / `code-architect` / `code-reviewer` の定義には既定の出力上限を書いてある（`.claude/agents/*.md`）。呼び出し側で上書きするときはプロンプト内に明示する。

## 応答側のルール

- **既存ファイルの再掲をしない**: 読ませた内容を応答にそのまま貼らず、要約と `file:line` 参照で済ませる
- **差分は Edit ツールで**: 変更は差分だけ送る。ファイル全量の貼り直しは避ける
- **ツール結果のダンプを垂れ流さない**: 要点だけ拾って応答する

## 作業前チェック

大きめのタスクに着手する直前に自問する：

- [ ] 全文読む必要があるか。Grep で絞れないか
- [ ] 3 ファイル以上跨ぐなら委譲したか。起動数は複雑さに見合っているか
- [ ] 委譲プロンプトに返却量の上限を書いたか
- [ ] 同じファイルを再度全読みしようとしていないか
- [ ] 応答に長大なコード貼付けを含めていないか
